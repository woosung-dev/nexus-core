# 블레싱 클라이언트 시안 3종 (만듦새 라운드)

`docs/prototypes/blessing-multibot-2026-08-06/` 의 후속입니다.
`compare.html` 을 열면 세 시안을 같은 상태로 나란히 조종할 수 있습니다. 빌드 도구는 필요 없습니다.

## 왜 다시 그렸나

직전 네 라운드는 정보 설계는 좋았지만 **차가웠습니다.** 원인은 규칙을 잘못 세웠기 때문입니다.
관리자 목업의 AI slop(라벤더 그라디언트 구름, 3D 일러스트, 로봇 아바타, 이모지)을 걷어내려고
`그라디언트 0 / 이미지 0 / 모션 3` 을 자기 규칙으로 세웠고, 그 결과 **절제와 만듦새를 같은 축으로
취급해** 표면·깊이·모션·브랜드 순간이 전부 사라졌습니다. 엠블럼은 24px 파비콘으로만 나왔습니다.

인터뷰에서 정해진 것:

| 질문 | 답 | 설계 반영 |
|---|---|---|
| 아쉬운 지점 | 구성이 안 맞다 + 차갑다 + 시각 언어가 밋밋 | 메인 구성을 다시 짜고, 모션·재질·도상을 넣었습니다 |
| 주 사용자 | 둘 다, 한 화면에서 | 표면은 쉽게, 원문·판차는 펼쳐서 |
| 범위 | 멀티봇 유지 | 14곳 로스터를 그대로 이어받았습니다 |
| 세련됨의 방향 | 모션 · 재질/깊이 · 이미지/도상 (활자 주도 아님) | 세 안이 이 셋을 **하나씩 나눠 주도**합니다 |
| 이미지 자산 | 없음 | 엠블럼 파생 커스텀 SVG 도상 체계로만 갔습니다 |
| 로그인 | 하나로 계정 SSO 단독 | 입력란이 없어 남는 면적을 브랜드 순간에 씁니다 |
| 기준 폭 | 데스크톱 | 1440px 에 마감을 몰고 390px 은 성립까지 |

## 구성이 왜 안 맞았나

`docs/guides/축복챗봇_운영원칙_v1.md:12-17` 은 첫 화면을 이렇게 규정합니다.

> 첫 화면은 다음 두 진입점을 보여줄 수 있다. **축복 정보 알아보기** / **고민 나누기**.
> 두 진입점은 별도 봇이 아니다.

네 라운드의 메인은 전부 **카탈로그**였습니다(표제어 색인 / 한 줄 접수 / 문서 총람).
운영 원칙이 명시한 의도 진입점을 어느 시안도 구현하지 않았습니다.
이번 세 안의 공통 원칙은 **의도가 먼저, 창구는 결과로** 입니다.

## 세 안

| | 명제 | 주도 기법 | 인용 기전 | 회색조 실루엣 | 강한 쪽 |
|---|---|---|---|---|---|
| **A 말문** | 홈은 목록이 아니라 **말을 여는 자리** | 모션·안무 | 우측 레일 | 본문 좌 + 자료 우 | 처음 오는 청년 |
| **B 자리** | 홈은 **내 진행 상황** | 재질·깊이·겹 | 문장 아래 끼움 카드 | 좌 레일 + 중앙 단 | 돌아오는 실무자 |
| **C 채광** | 홈은 **근거의 장면** | 이미지·도상 | 왼쪽 여백 방주 | 방주 좌 + 본문 우 | 설득이 필요한 자리 |

세 안 모두 14곳 로스터·답변 4유형·이관·데이터 계약을 공유합니다. 갈리는 것은 구성과 만듦새입니다.
**인용 기전이 셋 다 다른 것이 이번 라운드의 핵심 축입니다.** 같은 계약을 세 방식으로 풀어 두었으니
어느 쪽이 우리 사용자에게 맞는지 골라 주시면 됩니다.

## 시장 조사에서 가져온 것

`insane-search` 로 상용 RAG·챗봇 제품을 조사해 다음을 바꿨습니다. `_research/` 에 근거 스크린샷이 있습니다.

**1. 인용 표식을 위첨자 숫자에서 유형 알약으로.**
Perplexity 는 숫자를 버리고 발행처 이름 알약을 쓰고, Glean 은 제목과 아이콘을 강제합니다.
맨 숫자 각주는 현재 사양이 뒤처진 쪽입니다. A·B 는 문서 이름 알약, C 는 금선 표식을 씁니다.
알약 앞에 `&nbsp;` 를 넣어 홀로 줄바꿈되지 않게 했습니다.

**2. 유형 라벨은 등급이 아니라 종류다.**
처음에는 초록/회색 3단 배지를 쓰려 했으나 C2PA 2.0 UX 권고가 정면으로 반대합니다.
> 유효 상태를 표시하지 마라. 모든 라벨은 같은 색이어야 하며 신호등처럼 읽혀서는 안 된다.

그래서 `규정집 · 안내 · 지침 · FAQ` 를 **전부 같은 색**으로 두고, 표시가 붙는 것은
`개정 이전 판본` `문서 단위로만 확인` 같은 **부정적인 경우뿐**입니다.
표시가 없다는 것은 "검증됨"이 아니라 "적을 것이 없음"입니다.
이 결정은 `project_admin_evidence_labels_audit`(관리자 과대평가 11건)와 같은 방향입니다.

**3. 검색 타임라인이 접혀 영수증이 된다.**
Onyx 는 검색 단계를 흘리다가 소요 시간에서 멈추고, Glean 은 계획 카드를 "제목 + N개 완료"로 접습니다.
세 안 모두 검색 단계를 흘리다 `근거 2건 · 검색 2.1초` 한 줄로 접습니다.
**이 화면이 있어야 인용 0건과 검색 실패가 구분됩니다.** `reference_rag_grounding_underreports`
(인용 0 ≠ RAG 미작동)에 대한 화면 쪽 답입니다.

**4. 답변은 말풍선이 아니라 전폭 문서로.**
Perplexity·뤼튼·클로바X 를 실제 CSS 로 확인한 결과 진지한 정보 제품은 예외 없이
사용자 발화만 말풍선에 넣고 AI 응답은 전폭 문서로 놓습니다. 세 안 모두 그렇게 했습니다.

**5. 어시스턴트 아바타를 두지 않는다.**
정보 제품군은 응답에 얼굴이나 이름표를 붙이지 않습니다. 창구 정체성은 헤더에 한 번만 둡니다.

**6. 안전은 분류기를 기다리지 않는다.**
Replika 는 입력창 바로 위에 사용자가 먼저 누르는 도움 요청 자리를 둡니다.
세 안 모두 컴포저 위에 상시 열려 있는 자리를 두었습니다.
안내 카드는 **서비스의 목소리**이지 상담자의 말이 아니므로 시각적으로 분리했습니다.
번호는 보건복지부 안내 문구(2024-09-10 시행)가 명시하는 **109 와 마들랜** 둘입니다.
1393 은 폐지되었고 1588-9191 은 의무가 아닙니다.

**7. 8~15곳 구간에서는 묶음이 필수다.**
Glean 은 "부서당 5개 안팎, 팀이 실제로 쓰는 말로" 를 권합니다.
조직이 준 그룹 축이 없어 다섯 갈래를 세웠습니다. 조직이 축을 정하면 이 배열만 갈아 끼우면 됩니다.
또한 **"이 창구가 답하지 않는 것"** 을 적는 제품이 조사 대상 중 하나도 없었습니다.
세 안 모두 창구 상세에 이 문단을 둡니다.

**8. 한글 조판.**
리디북스·밀리의서재·토스·카카오 실 CSS 확인 결과 Pretendard 가 사실상 표준이고,
프리미엄 티어는 **읽기용 명조**를 따로 얹습니다. 그래서 규정집 인용문에만 마루부리를 씁니다.
`word-break: keep-all` + `overflow-wrap: break-word` 를 전역으로 넣었고 본문 자간은 0 입니다.
**Paperlogy 는 장식체(제목용)라 본문에 쓰면 안 되고, Freesentation 은 웹폰트 임베딩이
조건부 허용이라 별도 서면 허락 없이 쓰면 안 됩니다.** 직전 라운드들이 이 둘을 쓰고 있었습니다.

**9. 보라는 이 제품의 가장 큰 시각 위험입니다.**
Shape of AI 는 "보라가 AI 제품에서 압도적으로 지배적인 색이며 경험을 낡아 보이게 할 수 있다"고
경고합니다. 브랜드가 `#603B94` 이므로 색을 버릴 수는 없고, 대신 **AI 표식으로 읽히는 쓰임만**
걷어냈습니다. 그라디언트 0, 글로 0, 히어로 오브 0, **AI 응답 뒤에 깔리는 틴트 0.**
보라는 납작한 잉크·면·선으로만 씁니다. 인용을 켤 때도 배경을 칠하지 않고 밑선 하나로 잇습니다.

## 능력 표기

운영 원칙 §6 은 내부 분류와 RAG 동작 노출을 금지합니다. 그런데 "이 창구는 기억하지 않습니다"는
구현이 아니라 **사용자와의 약속**입니다. 선을 이렇게 그었습니다.

> **적는 것은 사용자의 기대와 어긋나는 쪽뿐이다. 기대대로면 아무것도 안 적는다.**

| 실제 설정 | 화면 문구 |
|---|---|
| `history_window: 0` | 앞 대화를 기억하지 않습니다 |
| `evidence_policy_mode: "strict"` | 근거를 못 찾으면 답하지 않습니다 |
| `use_rag: false` | 문서를 근거로 답하지 않습니다 |
| `is_active: false` | 지금은 답하지 않습니다 |
| `plan_required: PRO` | 카드에는 안 적고 부딪히는 자리에서만 |

화면에 절대 나오지 않는 말: RAG, strict, legacy, history_window, 시스템 프롬프트, 벡터, 내부 분류 이름.

대화 화면에서는 데스크톱 폭에서만** 드러납니다. 그래서 대조판 기본값을 「각 1100px」 로 두었습니다.
390px 에서 A·B·C 의 대화 화면은 사실상 같은 단일 단이고, 이건 잘못이 아니라 좁은 폭에서
옳게 접힌 결과입니다. 다만 **모바일이 주 사용처라면 세 안을 가르는 근거가 약해집니다.**

## 기술 메모

- 자립형 정적 HTML. 외부 의존은 폰트 CDN 뿐입니다. 엠블럼과 도상은 `<symbol>` 로 인라인해야
  `--em-field` / `--em-mark` 와 `currentColor` 로 재채색됩니다.
- 반응형은 미디어 쿼리가 아니라 **컨테이너 쿼리**입니다. `.app` 이 `container-type: inline-size` 입니다.
- `.screen` 의 표시 여부는 `[data-on]` 하나가 정합니다. **다른 클래스에서 `display` 를 선언하면
  숨겨야 할 화면이 함께 렌더됩니다.** 이번에도 `.thread{display:flex}` 로 같은 버그를 냈습니다.
- 모션은 `--motion` 단일 변수로 통제합니다. `animation:none` 대신 duration 을 0 으로 만듭니다.
  `none` 을 쓰면 `both` 가 풀려 시작 상태에 머무는 요소가 생깁니다.
- B안은 화면 전환에 View Transitions API 를 씁니다. 미지원 브라우저에서는 즉시 전환됩니다.

# 코드에 옮기기 전에 필요한 것 (백엔드 선행 과제)

세 시안이 그렸지만 지금 API 로는 값을 채울 수 없는 것들입니다. 번호는 급한 순서입니다.

### 1. 봇 ↔ 문서(코퍼스) 연결 - 없음

**창구를 구별하는 가장 중요한 축인데 클라이언트가 알 수 없습니다.**
`Bot` 모델에도 `BotResponse` 에도 담당 문서 목록이 없습니다.
여기 걸려 있는 것: 세 안의 창구 상세, 이관, 그리고 **C안의 문서 띠 전체**(창구가 보는 문서에서
역산한 값이라 이 값이 없으면 C안의 메인 절반이 성립하지 않습니다).
없으면 이관은 「근거 없음」으로 떨어뜨려야 합니다. 근거 없이 남의 창구를 지목하는 것은
문서명을 지어내는 것과 같은 종류의 거짓말입니다.

### 2. "이 질문은 어느 창구 담당인가" 의 판단 근거 - 없음

지금 그릴 수 있는 최대치는 이름·태그 문자열 매칭이고 그것은 근거가 아닙니다.
조사에서 확인한 참고 사례는 Glean 의 **투명한 라우터**입니다. 응답 위에 "Using Agent: X" 를 적고
사용자가 ✕ 로 빼고 일반 지식으로 다시 답하게 하며, "라우팅은 100% 정확하지 않습니다"를
문서에 그대로 적습니다. 이 방식이면 판단 근거가 완전하지 않아도 정직하게 출시할 수 있습니다.

### 3. `use_rag` 가 `BotResponse` 에 없음

### 5. 클라이언트 타입이 실제 응답보다 좁음

### 6. `BotResponse` 가 공개 엔드포인트로 `system_prompt` 를 내보냄

`backend/app/api/v1/endpoints/bots.py:18` 의 목록 엔드포인트가 `BotResponse` 를 쓰고,

### 7. 인용 대기 상태

`ChatProvider.tsx` 의 백필 폴링(2초 × 15회, 실측 약 15초)에 진행 상태가 노출되지 않습니다.
컨텍스트가 내보내는 값에 폴링 여부가 없어 바인딩할 변수가 없습니다.
세 안 모두 이 상태를 그렸고, 조사 결과 이 화면은 있으면 좋은 것이 아니라
**인용 0건과 검색 실패를 구분하는 유일한 수단**입니다.

### 8. 빈 상태를 셋으로 나눌 값

「근거 없음」(검색은 됐으나 대목 없음) · 「검색 실패」(시스템 오류) · 「담당자 연결 실패」는
사용자가 할 일이 다른데 지금 API 로는 구분할 수 없습니다.
Zendesk 는 이 셋을 각각 별개의 시스템 응답으로 모델링하고, 특히 **담당자 연결 실패**를
따로 둡니다. 일요일 밤에 실제로 발생하는 상태입니다.
