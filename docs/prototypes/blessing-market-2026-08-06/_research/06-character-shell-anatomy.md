# 캐릭터 챗봇 서비스 — 앱 셸 구조 해부

조사일: 2026-08-06 · 방법: Playwright 실접속(라이브 클릭·`getComputedStyle`·`getBoundingClientRect` 측정) + App Store 스크린샷 실측 + WebSearch/WebFetch 2차 자료 보완

**목적**: 이번 조사는 랜딩 마케팅 컨셉이 아니라 **로그인 전후 실제로 켜지는 "앱 셸" 구조**(로스터 그리드/리스트, 카드 해부, 내비, 랭킹 모듈, 채팅 진입 동선, 온보딩 타이밍)를 실측 해부한다. 직전 라운드 조사 `docs/prototypes/blessing-unbound-2026-08-06/_research/01-character-chatbot-services.md`가 랜딩·브랜드 톤 관점(무엇을 "훔쳐올지")을 이미 다뤘으므로 그 결론은 반복하지 않고, 이번 라운드의 다른 조사(`07-rag-shell-anatomy.md`=RAG 제품 워크스페이스, `08-visual-mood.md`=색상·폰트 실측)와도 각도를 분리했다.

**신뢰도 표기 원칙**
- **[실측]** = 이번 세션에서 Playwright로 직접 접속·클릭·측정
- **[실측-앱스토어]** = App Store 마케팅 스크린샷을 직접 열어 확인(실제 UI 캡처이므로 텍스트 2차 자료보다 신뢰도 높음, 다만 마케팅 목적으로 선별된 화면이라는 한계는 있음)
- **[2차]** = 헬프센터·리뷰·공식 문서 등 텍스트 자료
- **[추정]** = 여러 자료를 종합한 추론, 실물 미확인

## 0. 조사 중 특이사항 — 광고 리디렉션

크랙(crack.wrtn.ai)과 제타(zeta-ai.io)는 실측 세션 도중 카드 클릭 또는 페이지 체류만으로 **Pinterest·네이버 클로바 등 제3자 사이트로 강제 리디렉션되는 현상이 반복 발생**했다(각 서비스에서 2회 이상). 클릭한 요소와 무관하게 일어난 경우도 있어 페이지에 삽입된 광고 스크립트의 자동 리디렉션으로 추정된다. 이 때문에 크랙의 "카드→상세 모달→대화 시작" 이후 단계(로그인 요구 여부)는 완전히 재현하지 못했다. **[실측, 원인은 추정]** 두 서비스 모두 무료 이용자 대상 광고 기반 수익모델을 쓰는 것으로 보이며, 이는 우리 제품(사내 SSO 포털, 광고 없음)과 셸 설계 전제 자체가 다르다는 방증이기도 하다.

### 1.1 크랙 (crack.wrtn.ai) — wrtn, 한국

| 항목 | 실측 내용 |
|---|---|
| 비로그인 첫 화면 | **완전 브라우즈형.** 로그인 없이 전체 콘텐츠 그리드 즉시 노출. 화면 좌하단에 고정된 로그인 유도 카드(카카오·Google 아이콘)가 있지만 콘텐츠를 가리지 않음 [실측] |
| 홈 로스터 구조 | 캐릭터 탭 기준 **4열 그리드**(1440px 데스크톱, 좌측 약 260px는 고정 로그인 카드 영역이라 실제 그리드는 우측 ~1180px에 4열). 반응형 클래스 실측: `basis-1/2 sm:basis-1/3 md:basis-1/4`류 — 모바일 2열→태블릿 3열→데스크톱 4열 [실측: `getBoundingClientRect`] |
| 카드 종횡비·크기 | 카드 전체 208×303px, 그 중 **이미지 영역은 정확히 1:1 정사각형(208×208px)**, 하단 95px가 텍스트 블록(이름·설명·핸들). 이미지와 텍스트가 물리적으로 분리된 구조 [실측: `getBoundingClientRect`, cdn URL `width=400` 확인] |
| 카드 해부 | 이미지(1:1, 모서리 radius 약 8px, 그림자 없음) + 좌상단 대화수 배지(말풍선 아이콘+"24.5K"류, 만 단위 아닌 K 단위) + 하단 화이트 여백에 이름(볼드)·1~2줄 설명·"@제작자핸들"(작은 빨간 인증 아이콘 동반). "요즘 트렌드" 섹션에서는 카드 좌상단에 **1~4 랭킹 숫자**가 대화수 배지와 동시에 얹힘 [실측] |
| 내비 | **상단바만**, 좌측 레일 없음. 로고 + 탭(스토리/캐릭터/내 작품/이미지) + 중앙 검색바 + 우측 코인 아이콘·프로필 아이콘 [실측] |
| 랭킹/추천 모듈 | 섹션이 매우 잘게 쪼개짐 — 추천/신규 랭킹/여성 인기/남성 인기/오늘 신작(카테고리 칩 10개+ 가로 스크롤) → "떠오르는 신예 창작자들"(가로 캐러셀) → **"요즘 트렌드"(1~4위 랭킹, "전체보기" 링크)** → "캐릭터 모아보기"(정렬 드롭다운 "대화 많이 나눈 순", 무한 스크롤 그리드, 인기 카드는 M 단위까지 상승) [실측] |
| 채팅 진입 동선 | **카드 클릭(1) → "캐릭터 정보" 모달 오픈(이미지 확대+좋아요수+이름+팔로우 버튼+태그 3종+설명+"대화하기" CTA) → "대화하기" 클릭(2) = 2클릭.** 모달은 페이지 이동 없이 오버레이로 뜸 [실측]. "대화하기" 클릭 이후 로그인 요구 여부는 광고 리디렉션으로 재현 실패(§0) — 업계 관례상 실제 메시지 전송 시점에 로그인 요구가 유력하나 **[추정]** |
| 온보딩 | 첫 방문 시 로그인과 무관하게 **1회성 취향 온보딈 모달**(성향 3택, 스킵 가능) — 이번 세션에서는 직접 트리거되지 않았으나 직전 라운드 조사에서 확인됨 **[2차: 자체, 직전 라운드 실측]** |
| 컬러·타이포 | 배경 순백(`rgb(255,255,255)`), 폰트 `Pretendard, "Apple SD Gothic Neo", system-ui`, 활성 탭 필 배경 `rgb(255,68,51)`(코랄레드, #FF4433) — 이번 세션에서 독립 재실측 [실측] |

### 1.5 보너스(간략) — Talkie, Replika

우선순위 5번(여력 시)으로, 직전 라운드 조사에서 이미 상세 실측이 되어 있어 이번 라운드는 셸 해부 관점에서 핵심만 재인용한다 **[2차: 직전 라운드 실측]**.

- **Talkie**: 좌측 고정 사이드바(Notion/Discord류, Talkie 만들기/이미지 생성/발견/검색/커뮤니티) + 상단 검색바 — 조사 대상 중 유일하게 c.ai/Poe 없이도 "좌측 레일형" 내비를 쓴 사례. 로스터는 7열 밀집 그리드(카드 간격 거의 0, 정사각형에 가까운 카드). 온보딩은 콘텐츠 접근을 막지 않지만 **대명사·연령대 선택 모달이 닫기 불가**(다크패턴).
- **Replika**: 로스터/그리드 자체가 없는 유일한 사례 — 캐릭터 여러 명 중 고르는 제품이 아니라 "나만의 동반자 하나"를 파는 제품이라 셸 문법이 근본적으로 다름. 앱스토어 유도형 CTA, 웹에서 즉시 채팅 시작 없음.

## 2. 서비스 간 수렴·분기 패턴 (7개)

1. **로스터의 형태는 서비스 정체성에 따라 그리드/리스트/피드 세 갈래로 갈린다.** 로그라인 소비형(크랙·제타)=그리드, 유틸리티 카탈로그형(Poe)=리스트, 관계 몰입형(character.ai 모바일)=단일 카드 피드. 하나의 "업계 표준 그리드"는 없다 — 제품이 파는 것(콘텐츠 vs 도구 vs 관계)이 로스터 형태를 결정한다. [실측 종합]
2. **비로그인 관문은 완전 게이트 아니면 완전 브라우즈, 중간이 없다.** c.ai·Poe(둘 다 이미 브랜드 인지도가 검증된 톱티어)는 콘텐츠를 하나도 안 보여줘도 가입 전환이 되는 반면, 크랙·제타(상대적으로 신규/로컬 브랜드)는 콘텐츠부터 연다. **브랜드 신뢰 자산의 크기가 게이트 여부를 결정**하는 것으로 보인다. [실측+추정]
3. **카드 배지는 좌상단=정량 지표, 우상단=상태/이벤트 리본이라는 위치 문법이 크랙·제타 양쪽에서 동일하게 관찰된다.** 심지어 두 서비스 모두 한 카드에 배지 2~3종이 동시에 얹히는 밀도까지 유사하다. [실측]
4. **내비 레일의 위치는 "브라우징 축"이 세로냐 가로냐로 갈린다.** 좌측 사이드바(Talkie, Poe 데스크톱, c.ai 데스크톱 추정)는 텍스트/리스트 중심 탐색에, 상단바(크랙, 제타)는 이미지 그리드 스크롤에 붙는다. 우리처럼 로스터가 카드 그리드/리스트 어느 쪽이든 될 수 있는 제품은 이 상관관계를 참고할 만하다. [실측+2차 종합]
5. **그리드형만 상세 모달을 거치고, 리스트/피드형은 클릭 즉시 대화로 들어간다.** 크랙은 카드→모달→"대화하기"(2클릭), Poe는 리스트 행→즉시 대화(1클릭), c.ai 피드는 카드=미리보기라 사실상 즉시 진입으로 추정된다. **이미지가 카드의 전부인 서비스일수록 "고르는 행위"에 별도 확인 단계를 끼워 넣고, 텍스트가 카드의 절반인 서비스일수록 확인 단계 없이 바로 들어간다**는 상관관계로 읽힌다. [실측+추정]
6. **랭킹·순위 넘버링은 그리드형(크랙·제타)의 전유물이고, 리스트/피드형(Poe·c.ai)에는 없다.** Poe는 "OFFICIAL" 인증만, c.ai는 팔로워/좋아요 수치 자체를 카드에 노출하지 않는다 — **경쟁 서사가 필요한 콘텐츠형과, 필요 없는 도구·관계형의 차이**로 보인다. [실측]
7. **온보딩(취향 선택·필수 동의)은 로그인 여부와 완전히 독립된 레이어로 존재한다.** 크랙(선택형 취향 모달)·제타(강제 동의 모달) 둘 다 로그인 전/후 상관없이 뜨고, c.ai·Poe는 애초에 게이트가 유일한 관문이라 이런 중간 레이어가 없다. **"로그인=1개의 관문"이 아니라 "관문이 여러 층일 수 있다"**는 게 이번 조사의 구조적 발견이다. [실측]

## 3. 이식 판정

### 채택할 것

- **카드 배지의 "좌상단=지표, 우상단=상태" 위치 문법.** 우리는 대화수 같은 인기 지표가 없으므로 좌상단 자리를 그대로 쓸 필요는 없지만, 우상단 리본 자리는 "신규 추가"·"최근 업데이트" 같은 **중립적 상태 배지 1종**으로 변형해 채택할 가치가 있다. (근거: 크랙·제타 양쪽에서 독립적으로 관찰된 동일 위치 문법 — §2-3)
- **온보딩과 로그인 게이트를 별개 레이어로 설계하는 아키텍처 원칙.** 우리는 SSO 단일 관문이라 크랙식 "취향 온보딩 모달"이 그대로 필요하진 않지만, 로그인 이후 홈 최초 진입 시 1회성 안내(예: "이 포털에서 할 수 있는 것" 툴팁)를 로그인 절차와 분리된 레이어로 둘 수 있다는 구조적 시사점은 유효하다. (근거: §2-7)
- **Poe의 "채팅 헤더에 봇 프로필 요약을 계속 노출"하는 패턴.** 팔로워 수는 없애더라도, 봇 이름·한 줄 역할 설명·속성 배지를 채팅 화면 상단에 계속 유지하는 것은 **여러 봇을 오가는 사용자가 "지금 어느 봇과 대화 중인지" 잊지 않게 하는 실용적 장치**로, 우리 제품(문서 도메인이 봇마다 다름)에 직접 유용하다. (근거: §1.4 Poe 채팅 진입 동선)
- **상단바 중심 내비 + 그 안에 검색·카테고리 칩을 통합하는 구조(크랙·제타형).** 좌측 레일보다 셸이 가볍게 느껴지고, N-가변 로스터 브리프의 "그리드/리스트 전환"과도 잘 맞는다. (근거: §1.1, §1.3, brief의 콘텐츠-불가지론 셸 2번 원칙과 정합)
- **리스트형(Poe)의 "클릭 즉시 대화 진입" 동선.** 봇 개수가 적고 지표가 없는 우리 제품은 크랙처럼 모달을 하나 더 끼울 이유가 약하다 — 카드/행 클릭 한 번으로 바로 대화 화면으로 넘어가는 편이 마찰이 적다. (근거: §2-5)

### 버릴 것

- **랭킹 리본·1~N위 넘버링·"요즘 트렌드" 같은 순위 서사.** 우리 봇은 각자 다른 문서 도메인을 다루는 파트너 관계지 서로 경쟁하는 콘텐츠가 아니다 — "인사봇이 재무봇보다 인기 순위 4위"라는 문장 자체가 성립하지 않는다. (근거: §1.1, §1.3, §2-6, brief의 슬롭 블랙리스트 "별점/대화수 가짜 지표"와도 정합)
- **대화수·좋아요·팔로워 같은 정량 지표 배지 전반.** 우리는 이 데이터 자체가 없다(brief에도 "지표 데이터 없음" 전제). 없는 걸 채우려고 가짜 숫자를 넣는 유혹이 가장 위험한 함정이다(§4). (근거: §1.1~1.4 전 서비스 공통)
- **제타식 이미지 위 텍스트 오버레이 카드.** 실사/일러스트 이미지 위라면 대비 관리가 가능하지만, 우리 아바타는 시드 기반 기하학적 패턴(brief 3번 원칙)이라 오버레이 텍스트의 명도 대비를 예측하기 어렵다. 크랙식 "이미지+화이트 여백 분리"가 우리에게 훨씬 안전하다(직전 라운드 결론 재확인). (근거: §1.1 vs §1.3 카드 해부 비교)
- **크랙·제타식 강제 폭 축소(모바일 웹을 데스크톱에 그대로 늘리는 것)나 Talkie·Replika식 앱 다운로드 유도.** 우리는 사내 SSO로 접속하는 업무용 데스크톱 웹이 주 채널이라 애초에 반대 방향의 제품이다. (근거: §1.3, §1.5)
- **크랙의 카테고리 칩(로맨스/판타지 등 장르 태그) 그대로 이식.** 장르 개념 자체가 우리에게 없다. (근거: 아래 "변형할 것" 참조)

### 변형할 것

- **카테고리 칩: 장르 태그 → 업무 영역 태그.** 크랙·제타는 장르(로맨스/판타지/스릴러)로 칩을 나누지만, 우리는 Poe의 "기능형 칩"(Official/Image/Video처럼 봇이 무엇을 하는지) 쪽이 더 가까운 참조 모델이다 — 봇의 업무 영역(brief의 태그 합집합 파생 원칙)으로 변형해 채택. (근거: §1.4 Poe 카테고리 칩 vs §1.1/§1.3 장르 칩 대비)
- **크랙의 "카드→상세 모달→대화 시작" 2단계 흐름 → 축소된 확인 단계로 변형.** 모달 전체를 가져올 필요는 없지만, 클릭 즉시 대화창이 열리기 전에 **봇의 역할·인용 범위를 한눈에 보여주는 짧은 서브헤더**(모달이 아니라 채팅 화면 상단 고정 영역) 정도로 축소해 "이 봇이 뭘 아는지" 신뢰 신호를 유지할 수 있다. (근거: §1.1 모달 구성요소 중 태그·설명 부분만 선별적으로 재사용)
- **랭킹 모듈 → "최근 업데이트" 단일 배지로 축소.** 순위 매기기는 버리되, 어떤 봇의 문서가 최근에 갱신됐는지 알려주는 건 우리 제품(문서 기반 신뢰성)에 실질적 가치가 있으므로 격을 낮춰 재활용. (근거: §1.1/§1.3 랭킹 모듈 관찰 + brief의 "실제 기능 표면" 제약과 정합)

## 4. 함정 — 소비자 캐릭터 앱 문법을 문서 Q&A에 그대로 이식하면 어색해지는 지점

1. **가짜 지표의 유혹.** 조사 대상 4곳 모두 카드에 정량 지표(대화수·좋아요·팔로워)가 핵심 신뢰 신호로 박혀 있다. 우리는 이 데이터가 없는데, 셸을 "그럴듯하게" 채우려다 임의의 숫자를 넣으면 brief가 명시적으로 금지하는 슬롭이자 실제로도 기만이 된다.
2. **순위/경쟁 서사가 논리적으로 성립하지 않는다.** 크랙·제타의 "요즘 트렌드 1~4위"는 콘텐츠가 서로 대체재(어느 캐릭터든 골라도 됨) 관계일 때만 말이 된다. 우리 봇은 도메인이 겹치지 않는 보완재(인사봇과 재무봇은 경쟁하지 않는다) — 순위를 매기는 순간 "왜 이 봇이 저 봇보다 아래인가"라는 답할 수 없는 질문을 스스로 만들게 된다.
3. **카드 카피의 정보 밀도 문법이 반대다.** 캐릭터 앱 카드는 감성적 후킹 한 줄("XX를 하면 어려지는 당신의 파트너")로 충분하지만, 문서 Q&A 봇 카드는 "이 봇이 정확히 무엇을 아는지"(예: 복무규정·급여·연차 등 인사 전반)를 알아야 신뢰가 생긴다. 캐릭터 앱의 카피 길이·톤을 그대로 가져오면 후킹은 되지만 정작 사용자가 봇을 고를 정보를 못 얻는다.
4. **소셜 증명 지표(팔로워·구독)는 개념 자체가 성립하지 않는다.** Poe의 "255.8K followers"는 사내 SSO 단일 관문 제품에는 팔로우할 대상(다른 유저의 공개 프로필)이 애초에 없으므로 이식 시도 자체가 범주 오류다.
5. **character.ai식 "For You" 몰입형 단일 카드 피드는 로스터 개념과 정면 충돌한다.** 한 번에 한 캐릭터씩 몰입해서 넘기는 방식은 "여러 봇 중 지금 필요한 걸 훑어보고 고른다"는 우리 제품의 핵심 행위(그리고 brief의 N-가변 로스터 원칙)와 근본적으로 다른 사용 패턴이다 — 봇이 60개로 늘어도 "홈에서 훑어보고 고르는" 경험이 유지돼야 하는데, 피드형은 그 훑어보기 자체를 없앤다.
6. **제타의 이미지 오버레이 텍스트는 우리 아바타 체계와 충돌한다.** 실사·일러스트 이미지는 어두운 영역을 골라 흰 텍스트를 얹으면 되지만, 시드 기반 기하학 아바타는 명도 분포를 예측할 수 없어 대비 실패 리스크가 구조적으로 더 크다.
7. **크랙·제타의 배지 과적재(한 카드에 3종 이상 동시 노출)는 우리 스케일에서 더 어색해진다.** 원래도 소수 정예 봇 라인업에는 랭킹 서사가 안 맞는다고 지적됐는데(직전 라운드), 이번 조사로 배지가 겹겹이 쌓이는 밀도 자체가 "장사가 잘 되는 진열대" 문법이라는 게 재확인됐다 — 봇이 3~10개인 우리 홈에 이 밀도를 그대로 옮기면 정보가 아니라 소음이 된다.
