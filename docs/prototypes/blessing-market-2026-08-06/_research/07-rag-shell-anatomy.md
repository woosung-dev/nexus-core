# 상용 RAG 제품 — 앱 셸(로그인 후 워크스페이스)과 인용 UI 해부

조사일: 2026-08-06
목적: 로그인 후 실제 사용되는 홈/워크스페이스/채팅 셸과 인용 UI 실물을 해부해 우리 제품(문서 기반 멀티봇 RAG 포털, 최대 강점=인용 UI)에 이식할 패턴을 찾는다.
선행 조사: `docs/prototypes/blessing-unbound-2026-08-06/_research/02-rag-product-landings.md`(랜딩 페이지 관점, 마케팅 카피 중심) — 이번 조사는 로그인 후 셸에 집중하며 랜딩 페이지 내용은 반복하지 않는다.

**방법 및 신뢰도 표기 원칙**: 각 관찰 항목 끝에 근거 유형을 표기한다.
- **[관찰]** = WebFetch/Playwright로 실접속해 직접 확인
- **[2차]** = 공식 문서·헬프센터·리뷰 사이트·UX 갤러리(스크린샷 기반 해설)를 인용
- **[추정]** = 여러 2차 자료를 종합한 합리적 추론이며 실물 미확인

로그인이 필요한 제품(NotebookLM, Perplexity, Chatbase, CustomGPT.ai, Allganize, Glean)은 대부분 공식 헬프센터/개발자 문서·UX 해부 사이트(aiuxplayground.com, shapeof.ai, aydesign.ai)로 보완했다. 세 사이트 모두 스크린샷을 기반으로 텍스트 해설을 쓰는 곳이라 "실물 스크린샷 확인"에 준하는 신뢰도로 판단해 2차 자료로 명시했다.

## 1. 제품별 셸 해부

### 1.1 NotebookLM(Gemini Notebook) — notebooklm.google

**홈/워크스페이스 구조**
첫 화면은 **노트북 카드 그리드**다. 각 카드는 자동 할당된 이모지, 소스 수, 생성일, 오디오 재생 버튼을 포함하고 최근 항목/공유 노트북/제목/다운로드 등으로 정렬 가능하다. "새 노트북 만들기" 버튼을 누르면 빈 작업공간이 열리고, 소스 업로드 팝업이 바로 뜬다. [2차: support.google.com/notebooklm/answer/16206563, WebSearch 스니펫 종합]

**코퍼스 노출 방식**
노트북 = 코퍼스 단위. 카드에 "소스 수"가 바로 표기되어 "이 노트북이 몇 개 문서를 아는지"가 목록 단계에서부터 보인다. 소스는 최대 50개까지(과거 5개에서 상향)이며, "Discover Sources" 기능으로 웹에서 소스를 찾아 추가할 수도 있다. [2차: 여러 매체 종합]

**채팅 셸**
2026년 인터페이스는 **소스(좌) / 채팅(중) / 스튜디오(우) 3분할**로 고정되어 있다. 소스 패널에서 개별 소스를 체크/해제해 답변 범위를 조절하고, 스튜디오 패널에서 학습가이드·브리핑 문서·마인드맵·오디오 개요 같은 파생 산출물을 생성한다. 필요시 소스 뷰어와 노트 편집기를 나란히 확장하는 등 레이아웃이 유동적이다. [2차: academictech.uchicago.edu, jeffsu.org 등 종합]

**인용 UI(핵심)**
인용은 **회색 타원 안의 작은 숫자**로 답변 텍스트에 인라인으로 붙는다. 호버 시 미리보기가, 클릭 시 좌측 소스 패널이 열리며 **정확한 위치가 하이라이트**된다("Source guide"). Source guide는 단순 하이라이트에 그치지 않고 해당 소스의 요약과 핵심 주제 목록까지 함께 보여주는 **작은 패널형 문서 브리핑**이다. [2차: codecademy.com, datacamp.com, 여러 사용 가이드 종합]
전 라운드 조사에서 직접 확인한 마케팅 페이지 스크린샷("See the source, not just the answer" 카드)도 이와 일치: 다크 UI 카드 안에 하이라이트된 원문 + 인라인 번호 칩 ①. [관찰: notebooklm.google, 전 라운드 Playwright 스크린샷]

**신뢰 신호 배치**: 온보딩(소스 업로드 직후)이나 빈 상태에 별도 신뢰 카피는 확인되지 않음 — 대신 "인용 없이는 답하지 않는다"는 원칙이 구조 자체(항상 인용 붙은 응답)로 구현되어 있다는 게 여러 가이드의 공통 서술.

### 1.2 Perplexity — perplexity.ai

**홈/워크스페이스 구조**
전 라운드 조사에서 직접 확인한 대로, perplexity.ai 루트는 마케팅 랜딩이 아니라 **로그인 전 제품 UI 자체**다. 좌측 사이드바에 신규 검색/Computer/아티팩트/프로젝트/세션 메뉴, 중앙에 검색창 하나. [관찰: 전 라운드 Playwright 스크린샷]
로그인 후 사이드바는 **Threads(개별 대화) → Library(전체 히스토리, 최신순) → Spaces(Pro 기능, 프로젝트 단위로 스레드·공유파일·커스텀 지침을 묶는 상위 컨테이너)**의 3단 계층으로 구성된다. Space는 Library 위에 얹히는 구조로, Space 안의 스레드도 Library에 동시에 노출된다. [2차: perplexity.ai 공식 헬프센터 "Where did my threads go?", llmnesia.com 종합]

**코퍼스 노출 방식**
Perplexity는 고정 코퍼스가 아니라 웹 전체 + 사용자가 Space에 넣은 파일이 소스이므로 "이 봇이 아는 것"이라는 개념 자체가 다른 제품과 다르다. Space 단위로 "공유 파일" 목록이 있다는 것만 확인, 파일 수 배지 등 세부 UI는 미확인.

**인용 UI(핵심, 조사 대상 중 사실상의 업계 표준)**
마커는 **도메인 파비콘 칩** 형태 — 예: `northjersey +3`, `foxsports +2`처럼 발행처 도메인명을 먼저 보여주고 복수 소스는 `+N`으로 압축한다(숫자만 있는 각주가 아니라 "출처 자체"가 마커). 클릭/상호작용은 3단 깊이:
1. **칩 팝오버** — 제목·스니펫·소스 간 페이지네이션(1/2)
2. **우측 사이드바** — "10 sources" 클릭 시 답변 탭을 벗어나지 않고 모든 카드를 나열
3. **Links 탭** — 같은 질의를 감사(audit) 관점으로 재구성한 전용 화면, 모든 참조를 스캔 가능한 카드로

각 카드는 파비콘·도메인·제목·스니펫·섬네일로 구성. 답변 상단에는 "파비콘 스택 + 'N sources'"가 공유/복사/재작성 버튼과 나란히 배치된다. [2차: aiuxplayground.com/teardowns/perplexity/citations 상세 해부 페이지, 스크린샷 기반 UX 티어다운]

**위치 표기 심도**: 웹페이지 단위(도메인·제목)까지이며 페이지/문단 단위 표기는 없음 — 웹 검색 특성상 당연한 한계.

### 1.3 ChatPDF / Humata / AskYourPDF — 문서 뷰어+채팅 스플릿 셸 3종

세 제품 모두 **"좌: 채팅, 우: 문서 뷰어" 스플릿 뷰**라는 동일한 셸 문법을 공유한다.

**ChatPDF**
사이드바이사이드 인터페이스에서 클릭 가능한 인용이 즉시 PDF의 정확한 원문으로 스크롤 이동한다. 챗봇 명령어로도 내비게이션 가능("Go to page 5", "Next page", "Highlight [텍스트]") — 즉 **인용 클릭 스크롤 + 자연어 명령 두 경로**를 모두 지원. 페이지 검색·줌·인용 점프·스플릿뷰 체크가 뷰어 표준 기능. [2차: chatpdf.com, pdfgear.com 가이드 종합]

**Humata**
동일하게 **좌: AI 채팅, 우: 문서**의 스플릿 레이아웃. 답변의 인용이 하이라이트된 링크로 표시되며 클릭 시 원본 PDF의 정확한 구절로 스크롤한다("Get answers you can trust" — 기능명 자체가 "Highlights citations"). [2차: mspoweruser.com Humata 리뷰, 공식 humata.ai 종합. 전 라운드 조사에서 히어로 스크린샷 4장 존재는 확인했으나 인앱 CSS 디테일은 미확인]

**AskYourPDF**
여러 문서를 동시에 열어 **하나의 통합 채팅 인터페이스**에서 비교·종합할 수 있다는 점이 ChatPDF/Humata와의 차이 — 단일 문서 스플릿뷰가 아니라 다문서 통합 채팅에 가깝다. "정확한 인용" 제공 + 학술 인용 스타일 자동 포맷 생성(APA/MLA 등) 기능이 특이점 — 챗봇 인용을 학술 참고문헌 형식으로 export하는 것은 이 조사에서 유일하게 발견된 사례. [2차: askyourpdf.com, atlasworkspace.ai 종합]

**세 제품 공통 관찰**: 문서가 1(또는 소수)개일 때 "코퍼스 노출"이라는 개념 자체가 거의 필요 없다 — 뷰어에 문서가 항상 떠 있으므로 "이 봇이 무엇을 아는지"는 질문할 필요조차 없이 화면에 이미 보인다. 이는 멀티문서·멀티봇인 우리 제품과 근본적으로 다른 전제.

### 1.4 Chatbase / CustomGPT.ai — 멀티봇 관리 셸

**Chatbase**
대시보드에서 "New AI Agent" 버튼으로 에이전트를 생성하고, 좌측 사이드바가 주 내비게이션(아이콘 전용 모드로 접기 가능)이다. 개별 에이전트 안에는 **Playground**(실시간 미리보기·테스트), **Build > Instructions**(동작 설정), **Channels**(배포 채널: Chat bubble 등), **Usage**(에이전트별 크레딧 사용량, 삭제된 에이전트 포함 필터 가능) 탭이 있다. 고객 대화는 별도 "Helpdesk" 대시보드에서 티켓처럼 채널 통합 관리된다. Playground 안에서 "Show sources"를 누르면 **해당 응답이 어떤 학습 데이터(파일/URL/Q&A)를 사용했는지**가 노출된다 — 즉 인용이 최종 사용자용 채팅창이 아니라 **운영자용 디버그 뷰**로 먼저 설계돼 있다는 점이 특징. [2차: chatbase.co/docs 공식 문서(quick-start, playground, workspace/usage) 종합]
정확한 다중 에이전트 "목록 카드" 레이아웃(그리드/리스트, 카드당 표시 정보)은 공식 문서에서 명시적으로 확인하지 못함 — LinkedIn 티저 게시물(2026)에 "새 대시보드" 언급만 존재, 시각적 확인 실패. [2차 불충분 → 이 항목만 미확인으로 남김]

**CustomGPT.ai**
운영자는 Settings > Chatbot Settings > **Citation 탭**에서 인용 노출을 켜고/끄고, **4가지 표시 모드** 중 선택한다: ① 인용 안 보임 ② 응답 끝에 모아서(클래식) ③ 응답 안에 번호 인라인 삽입 ④ 인라인+끝 요약 동시. 인용 헤더 문구·라벨·기본 펼침/접힘 상태까지 커스터마이즈 가능. 최종 사용자 화면에서는 스크롤 가능한 소스 리스트가 클릭 가능한 링크로 뜨고, OpenGraph 메타데이터로 미리보기 이미지까지 자동 생성된다. **이 기능 자체가 Premium 이상 유료 플랜 전용**이라는 점이 중요한 발견 — 인용 UI를 요금제 게이트 뒤에 두는 유일한 사례. [2차: docs.customgpt.ai/docs/how-to-activate-citations-for-your-ai-agent 공식 문서]

**두 제품 공통 관찰**: "여러 봇 관리"라는 우리와 가장 닮은 셸이지만, 정작 인용 UI 설계는 최종 사용자 경험보다 **운영자 설정값**으로 다뤄진다. 즉 이 카테고리 제품들은 인용을 "제품의 정체성"이 아니라 "켜고 끌 수 있는 기능 토글"로 취급한다.

### 1.5 Allganize(알리) / 한국어 시장 신뢰 신호 관행

**Allganize**
전 라운드 조사에서 랜딩 페이지 카피로 확인한 "Grounded in the original layout — 원본 문서에서 인용 구간을 직접 강조", "p.4 § 2.3 · layout preserved"가 이번에도 재확인됨. 공식 유저 가이드(guide.allganize.ai)의 "Conversation Answer Suggestions" 문서는 상담원용 **제안 답변 기능**(문서 검색 결과 미리보기 + "Use this answer" 버튼으로 답변 복사)을 다루고 있어, 일반 최종 사용자 챗봇 화면과는 다른 상담원(agent-assist) UX였다 — **인용을 최종 사용자에게 보여주는 화면과 상담원이 근거를 확인하는 화면을 분리**하는 설계로 추정됨. [관찰: guide.allganize.ai 공식 문서 / 인용 UI 세부는 이 문서에서 확인 실패, 랜딩 카피는 전 라운드 관찰]

**Upstage 다큐먼트 AI**
"AI가 생성하는 모든 답변이 업로드된 문서 내용에 기반하며, 어떤 문장의 어느 부분에서 정보를 가져왔는지 출처를 명확히 표시"한다는 서술이 다수 매체에서 반복 확인됨. 다만 실제 인용 UI 스크린샷(마커 모양, 클릭 동작)은 찾지 못함 — 문서처리(OCR/파싱) 기술 자체가 제품의 중심이고 챗봇 UI는 부수적으로 언급되는 수준. [2차: zdnet.co.kr 시연 기사 등, UI 세부는 미확인]

**AntDocs Chat(앤트피플, 한국 사내 RAG 챗봇 SaaS)**
"답변의 출처(파일/페이지/문단)를 함께 제공"한다고 명시. 데모 질문 예시(연차 신청, 보안 사고, 출장비 정산 등 사내 행정 시나리오)로 미루어 볼 때 **우리 제품과 도메인이 가장 가까운 한국 사례**(행정 규정 기반 Q&A)였으나, 화면 레이아웃·인용 마커 상세는 웹페이지에서 확인 불가 — 데모 상담을 통해서만 노출하는 방식(제품 자체를 공개 웹에 노출하지 않음). [관찰: antpeople.co.kr, UI 세부는 미확인]

**종합 관찰**: 한국 문서 기반 AI 시장은 대부분 **B2B 세일즈 데모/컨설팅 게이트** 뒤에 실제 제품 화면을 감추는 관행이 강하다(공개 웹에서 로그인 없이 접근 가능한 글로벌 소비자 제품 NotebookLM·Perplexity·ChatPDF류와 대비됨). "출처(파일/페이지/문단)" 같은 **문구 차원의 신뢰 신호는 글로벌 제품과 동일한 어휘**를 쓰지만, 실물 UI를 공개적으로 검증 가능한 곳이 거의 없다는 것 자체가 하나의 시장 특징이다.

### 1.6 Glean — 엔터프라이즈 검색 셸

**홈/워크스페이스 구조**: app.glean.com 로그인 또는 브라우저 확장 사이드바(Cmd+J / Alt+J 단축키, 페이지 우측 고정 탭 아이콘)로 진입. 사이드바 안에 Chat 탭(AI 어시스턴트)과 Search 탭(문서·사람 검색)이 공존. 설정에서 홈페이지(뉴탭)를 개인화할 수 있다는 언급은 있으나 빈 상태/기본 위젯 구성의 세부는 공식 문서에서 확인 실패. [2차: docs.glean.com Quick Start, developers.glean.com Sidebar]

**인용 UI(핵심, 조사 대상 중 가장 정교한 클레임-레벨 시스템)**
인용은 **인라인 마커 + 답변 하단 "View sources" 섹션**의 2단 구조. 인라인 마커는 근거가 필요한 진술 바로 뒤에 붙는다. 호버 시 컨텍스트 미리보기가 뜨고, "Deep-linked citations"(고급 기능)를 켜면:
- 응답 데이터에 `referenceRanges[].snippets[]` 배열로 **정확한 인용 텍스트 + 페이지 번호(선택값) + 전후 약 200자 문맥**이 포함됨
- 호버 팝오버가 인용 텍스트를 하이라이트하고 **주변 문맥까지 함께** 보여줌(우리 형광펜과 유사하되 "문맥"을 별도로 얹는 것이 차이)
- 클릭 시 원본 애플리케이션(Google Docs/Confluence/SharePoint 등)의 `sourceDocument.url`로 이동 — 단, PDF/PPT 등 일부 포맷에서만 정확한 페이지/오프셋 점프가 보장됨("not guaranteed for all sources"라고 공식 문서가 정직하게 명시)
- 인용 대상은 문서·파일뿐 아니라 **사람 레코드**(작성자/소유자)도 포함 — 이 조사에서 유일하게 "문서가 아닌 사람을 인용"하는 사례
- 기존 통합과 호환되도록 "additive and backward compatible"로 설계 [2차: docs.glean.com/user-guide/assistant/glean-chat/glean-chat-citations, developers.glean.com/guides/chat/deep-linked-citations 공식 문서 직접 인용]

**신뢰 신호 배치**: 전 라운드 조사에서 이미 확인했듯 Glean은 랜딩 페이지에서 인용을 세일즈 포인트로 거의 안 쓰고 ROI 지표·컴플라이언스 배지로 대체했다. 인앱에서도 이번 조사 결과, 인용은 "정확성 기능"으로 조용히 문서화되어 있을 뿐 온보딩이나 빈 상태에서 강조되는 정황은 발견하지 못했다 — 랜딩과 인앱의 신뢰 신호 전략이 일관됨.

## 3. 수렴 패턴 5~8개

1. **인용 마커는 항상 텍스트 안이 아니라 "레이어" 진입점이다.** 6개 제품 전부 숫자/칩 자체는 정보량이 적고, 클릭·호버가 열어주는 2차 레이어(팝오버·패널·뷰어 스크롤)에 실제 신뢰 정보를 담는다. "마커가 예쁜가"보다 "레이어가 몇 단계인가·각 단계가 무엇을 보여주는가"가 진짜 설계 변수다.
2. **깊이가 있는 제품일수록 클릭 동작이 다단계다.** Perplexity(팝오버→사이드바→전용탭), Glean(호버 미리보기→클릭 이동)처럼, 얕은 검증(호버)과 깊은 검증(전체 화면 이동)을 분리해 사용자가 원하는 깊이만큼만 파고들게 한다.
3. **"이 봇/노트북이 무엇을 아는가"는 목록 카드 단계에서 숫자로 미리 답한다.** NotebookLM의 소스 수 배지가 대표적 — 채팅을 시작하기도 전에 코퍼스 규모를 알려주는 것이 코퍼스형 제품의 공통 관행.
4. **문서 스플릿뷰(ChatPDF/Humata류)는 "클릭 즉시 원문 스크롤"이 핵심이고, 통합 채팅형(NotebookLM/Perplexity/Glean)은 "클릭 시 별도 패널이 열림"이 핵심이다.** 전자는 원문이 항상 화면에 있어 점프만 하면 되고, 후자는 원문이 화면 밖에 있어 패널을 소환해야 한다 — 우리 제품처럼 문서가 다수·상시 비노출인 경우 후자 문법(패널 소환형)이 구조적으로 더 맞다.
5. **정확한 위치 표기("p.4 §2.3", 페이지 번호)를 하는 제품은 소수(Allganize, Glean 딥링크)이고, 나머지는 문서/구절 단위에서 멈춘다.** 전 라운드 결론("위치 단위 구체화는 Allganize만 했다")이 이번 조사에서 Glean의 딥링크 인용으로 하나 더 늘었다 — 완전히 예외적인 소수 사례라는 결론은 유지되지만 "업계에 아예 없는 것"은 아님이 확인됨.
6. **멀티봇/멀티에이전트 관리 셸(Chatbase, CustomGPT.ai)은 인용을 최종 사용자 경험이 아니라 운영자 설정값으로 다룬다.** "인용을 켤지 끌지", "어디에 보일지"를 관리자가 고르는 토글로 만들고, 심지어 유료 플랜으로 게이트하기도 한다 — 인용을 제품의 정체성으로 삼는 제품(NotebookLM, Glean)과 뚜렷이 갈린다.
7. **"정직한 실패/한계 고지"는 문서에만 존재하고 UI 카피로는 거의 노출되지 않는다.** Glean의 "딥링크 점프가 모든 포맷에서 보장되지 않는다"는 개발자 문서에만 있는 문장이고, 최종 사용자 화면에 이런 한계 고지가 노출된다는 증거는 찾지 못했다 — 즉 "근거 없음/실패 상태"를 정직하게 말하는 제품은 이 조사에서 사실상 없었다(우리의 "근사 인용 정직 라벨"이 상대적으로 드문 설계라는 뜻).
8. **컬러/타이포 무드는 제품군에 따라 갈린다.** 코퍼스형(NotebookLM)은 라이트+쾌활한 손글씨 주석으로 소비자 온기를 의도적으로 넣었고, 검색형(Perplexity)은 다크+시네마틱, 멀티봇 관리형(Chatbase/CustomGPT.ai)과 엔터프라이즈형(Glean)은 다크/차콜+중립 산세리프로 "도구"임을 명확히 한다. 코퍼스 소유자가 개인/팀인 제품일수록 따뜻하고, 대규모 조직·B2B SaaS 운영 대상 제품일수록 차갑다.

## 4. 이식 판정

### 4-1. "우리 형광펜 근거 하이라이트보다 나은 사례가 있는가?"

**결론: 없다.** 이 조사에서 발견한 제품 중 "문서별 그룹 + 페이지 표기 + 형광펜 근거 하이라이트 + 본문 각주 + 근사 인용 정직 라벨"을 전부 갖춘 조합은 하나도 없었다. 각 제품은 이 조합의 부분집합만 가진다(Perplexity=마커 깊이만 강함/위치표기 없음, Allganize·Glean=위치표기만 강함/정직라벨 없음, ChatPDF류=점프만 강함/그룹핑 없음). 다만 두 가지는 우리에게 없는 **보완적 디테일**이라 훔쳐올 가치가 있다.

- **Glean의 "인용 스니펫 + 전후 문맥 200자"**: 우리는 정확히 인용된 문장만 하이라이트하는데, Glean은 그 앞뒤 맥락까지 호버에 곁들인다. 규정집처럼 "이 조항 앞에 예외 단서가 있었나?"가 중요한 도메인에서는 유용한 추가 레이어가 될 수 있다.
- **NotebookLM의 "인용 클릭 → 해당 문서 요약까지 동반된 패널"**: 우리도 문서별 그룹 패널이 있지만(이미 대상 문서 강조), 그 패널을 열 때 "이 문서 전체가 무엇에 관한 것인지" 한 줄 요약을 같이 보여주면 인용 하나를 넘어 문서 자체에 대한 신뢰까지 형성할 수 있다.

이 둘은 "우리 방식을 대체"하는 게 아니라 "우리 패널을 한 겹 더 두껍게" 만드는 보강안이다.

### 4-2. 채택

1. **NotebookLM식 로스터 카드 배지("문서 N종")** — 봇 홈 카드에 문서 수를 상시 노출. 채팅을 시작하기 전에 "이 봇이 몇 개 규정을 아는지"가 보이면 신뢰 형성이 그만큼 앞당겨진다. 근거: 1.1절, 대상 조사 6개 중 유일하게 목록 단계에서 코퍼스 규모를 숫자로 답하는 사례였고, 우리의 멀티봇 로스터 구조와 정확히 맞아떨어짐.
2. **Perplexity식 3단 깊이(팝오버→패널→전체보기)** — 지금 우리 각주가 클릭 시 패널로 바로 점프하는 구조라면, 그 전 단계로 가벼운 호버 팝오버(발췌 1~2줄)를 추가해 "패널까지 열 필요 없는 즉답형 확인"을 지원. 근거: 2절 비교표, Perplexity가 유일하게 얕은/깊은 검증을 명시적으로 분리한 사례.
3. **Glean식 클릭 시 목적지 보장 정직 고지 원칙(내부 규칙으로)** — "일부 포맷은 정확한 페이지 점프가 안 될 수 있다"를 UI에 숨기지 않고 관리자 문서/로그에 남기는 습관. 우리 도메인은 공문·스캔 문서가 섞여 있어 페이지 점프 실패 케이스가 실제로 생길 수 있는데, Glean처럼 "보장 안 됨"을 정직하게 기록해두는 태도를 개발 원칙으로 채택.

### 4-3. 버림

1. **NotebookLM/Glean식 고정 다단 워크스페이스(소스/채팅/스튜디오 3열, 검색+채팅 사이드바 병존)** — 근거: 3-1절과 5절. 코퍼스 편집이 일상 업무인 리서치/사내 검색 도구에는 맞지만, 우리처럼 "질문하고 답 받는" 소비자성 상호작용에는 패널 개수가 늘수록 초심자에게 인지 부하만 커진다. 우리는 채팅이 주 화면이고 인용 패널은 필요할 때만 여는 보조 레이어로 남겨야 한다.
2. **Perplexity식 도메인 파비콘 칩 스택(`+N`)** — 근거: 2절. 이는 "출처가 무작위 웹 전체"라는 전제에서 나온 압축 표기다. 우리는 소수의 승인된 정본 문서가 코퍼스이므로, 굳이 압축할 필요 없이 문서명을 있는 그대로 보여주는 현재 방식(문서별 그룹)이 오히려 더 신뢰감 있다. 칩으로 압축하면 "출처가 많아서 못 다 보여준다"는 인상을 주는데, 우리 도메인에서는 이게 불신 신호가 될 수 있다.
3. **CustomGPT.ai식 인용 표시를 유료 플랜 뒤에 게이트** — 근거: 1.4절. 인용은 우리 제품의 최대 강점이자 정체성이다. 이를 기능 토글이나 과금 대상으로 다루는 순간 "저건 원래 안 보여줘도 되는 부가기능"이라는 메시지를 스스로 보내는 셈이다.
4. **Chatbase식 "Show sources"를 운영자 디버그 뷰로만 두기** — 근거: 1.4절. 인용은 최종 사용자(질문자)를 위한 것이지 운영자 QA 도구가 아니다. 우리는 이미 최종 사용자 화면에 인용을 상시 노출하고 있으므로 이 패턴은 반면교사로만 남긴다.

### 4-4. 변형

1. **Allganize/Glean의 조항·페이지 단위 위치 표기 → 우리 도메인 어휘로 재작성.** "p.4 §2.3" 같은 법률·계약서 표기 관행을 그대로 쓰지 말고, 우리 규정집의 실제 단위(예: "제3장 2절", "2026년 개정판 p.12")로 자연스럽게 옮긴다. 근거: 이미 우리가 페이지 표기를 하고 있으므로 이는 "도입"이 아니라 "표기 어휘를 더 한국 행정문서다운 관행으로 다듬기"에 가깝다.
2. **NotebookLM의 "패널이 곧 문서 브리핑" 개념 → 우리 문서별 그룹 패널에 한 줄 요약 필드 추가.** 전면 도입(스튜디오처럼 별도 산출물 생성 기능까지)은 버리되, "이 문서는 무엇에 관한 것인가" 한 줄만 패널 상단에 얹는 가벼운 버전으로 변형해서 채택.
3. **Glean의 클레임 레벨(문장 단위) 인용 세분화 → 우리의 문서 단위 그룹핑과 절충.** Glean처럼 문장마다 각기 다른 마커를 촘촘히 붙이면 우리 도메인(공감·상담 톤 답변)에서는 텍스트가 각주로 뒤덮여 산만해질 위험이 크다. 대신 문단 단위로 하나의 각주만 붙이고, 그 각주가 여는 패널 안에서 "이 문단의 어느 문장이 어느 원문과 대응하는지"를 세분화해서 보여주는 절충안으로 변형.

## 5. 함정 — 도구형 셸 문법이 소비자 온기를 죽이는 지점

1. **다단 워크스페이스는 "일 잘하는 느낌"을 주지만 "환영받는 느낌"은 주지 않는다.** NotebookLM의 소스/채팅/스튜디오 3열, Glean의 검색+채팅 사이드바 병존은 둘 다 "생산성 도구"의 문법이다. 가정 상담·신앙 상담처럼 정서적 안전감이 중요한 도메인에서 첫 화면부터 패널이 3개 열려 있으면 "여기 뭔가 익혀야 할 도구가 또 하나"라는 피로감을 먼저 준다. 우리는 채팅을 절대적 주인공으로 두고 패널은 "부른 만큼만 나타나는" 보조여야 한다.
2. **운영자용 토글·설정 언어가 사용자 화면 카피에 새어 나오면 즉시 차갑다.** CustomGPT.ai의 "Citation 탭", "Personalize settings" 같은 관리자 문서의 어휘가 그대로 사용자에게 노출되는 순간(예: 빈 상태 문구에 "인용 기능이 비활성화되어 있습니다" 같은 시스템 로그체) 상담 도구가 아니라 SaaS 관리 콘솔처럼 읽힌다.
3. **"소스 수", "토큰 절감량" 같은 정량 배지는 양날의 검이다.** NotebookLM의 "소스 N개"는 신뢰 신호로 채택할 만하지만, Glean의 "110시간 절약", "124억 토큰 절감" 같은 ROI형 숫자를 그대로 들여오면 사람을 "처리 효율 지표"로 대하는 인상을 준다. 숫자를 쓰더라도 "이 봇이 아는 문서 12종"처럼 사용자가 검증에 쓸 수 있는 숫자만 남기고, 운영 효율을 자랑하는 숫자는 사용자 화면에 두지 않는다.
4. **신뢰도 배지(strong/mixed/weak/unsupported류, Consensus·scite.ai 계열)는 학술 논문 검증 도구의 어휘다.** 우리 도메인에 그대로 가져오면 "이 답변은 약한 근거입니다" 같은 라벨이 상담 상황에서 불안을 조장할 수 있다. 우리가 이미 쓰는 "근사 인용" 정직 라벨(문장체·설명형)이 이 계열보다 도메인에 훨씬 적합하다는 점을 이번 조사가 역으로 확인해준다 — 학술형 배지로 "업그레이드"하려는 유혹을 경계할 것.
5. **B2B 멀티봇 관리 셸(Chatbase/CustomGPT.ai)의 "에이전트 카드 + Usage 탭 + Channels 탭" 구조를 사용자용 로스터 홈에 그대로 옮기면 관리 콘솔처럼 보인다.** 이 구조는 운영자(관리자 대시보드)에게는 맞지만, 최종 사용자가 보는 봇 로스터 홈은 이런 "관리" 어휘(Usage, Channels, Build)를 완전히 걷어내고 "무엇을 물어볼 수 있는 친구/도우미인가"로 다시 번역해야 한다. 이미 우리 관리자(admin) 화면과 사용자(로스터 홈) 화면이 분리돼 있다는 전제하에, 이 분리 자체를 절대 흐리지 않는 것이 핵심 방어선이다.
