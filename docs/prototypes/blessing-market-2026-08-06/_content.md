# 공용 목데이터 콘텐츠 팩 — blessing-market-2026-08-06 (8회차)

3안(A 소비자 앱 셸 / B 문서 도구 셸 / C 하이브리드)이 전부 같은 콘텐츠를 쓴다.
축이 달라도 데이터가 같아야 대조가 성립한다. 봇 이름·문서명·규정 내용·인용문은 전부
UI 검토용 예시다. 실제 규정 원문이 아니다. (unbound 팩 계승 + 이번 라운드 확장)

## 서비스 정체 (계승 항목 단 둘)

1. **RAG(문서)기반 챗봇** — 승인 문서를 근거로 답하고, 근거를 인용으로 보여준다
2. **멀티봇** — 담당 문서가 다른 여러 창구(봇)가 있고, **계속 늘어난다**

서비스명 "블레싱" 기본. 워드마크·표기(한/영)는 안별 재량.

## 3뷰 구성 (인터뷰 확정)

한 HTML 파일 안에서 전환: **랜딩(관문)** → **#home(봇 로스터)** → **#chat(대화)**.
- 랜딩: 제품 소개 + 진입 CTA. 로그인은 **하나로 SSO ID/PW 단일 카드**
  (가입·소셜·이메일 로그인 없음 — "Google로 계속" 류 목업 금지).
- #home: N-가변 로스터. **N 스위치(8/24/60)** 를 데모 컨트롤로 노출해 확장성을 시연.
  검색 인풋 + 카테고리 칩(태그 합집합에서 파생) + 빈 상태 + 스켈레톤 상태 포함.
- #chat: 아래 목대화 1벌. 사이드바(세션 목록)는 목업 3~4행.

## 봇 데이터 계약 (frontend-client `BotResponse` 정합)

각 봇: `name` · `description`(2줄 이내) · `tags[]` · `is_verified`(Official 배지) ·
`plan_required`(FREE/PRO — 렌더는 안별 재량) · 특이 능력 표기(기대를 배신하는 쪽만).
별점·대화수·인기순 지표 **없음**(데이터가 없다 — 가짜 지표 금지).
화면에 절대 안 나오는 말: RAG, strict, 벡터, 시스템 프롬프트, 내부 분류명.

## 아바타 규칙 (3안 공통 구현 — 이니셜+컬러 시드)

이미지 없음 전제. 이름 해시 → 색상 시드, 이니셜 1자(한글은 첫 음절, 라틴은 첫 글자 대문자).

```js
function avatarSeed(name){
  let h = 0;
  for (const ch of name) h = (h * 31 + ch.codePointAt(0)) % 360;
  return h; // hue 0~359
}
// 배경: hsl(hue, S%, L%) — S·L은 안별 팔레트 토큰으로 재량(파스텔/딥 등)
// 전경 이니셜: 같은 hue의 저채도 암색 또는 팔레트 잉크색
// 모양(원/스쿼클)·질감은 안별 재량. 로봇 얼굴·이모지 금지.
```

같은 봇은 어느 안에서든 같은 hue가 나온다(대조 성립 조건).

## 채팅 목대화 1벌 (전 시안 공통 — 봇: 블레싱 네비게이션)

**사용자**: 축복식 준비 절차가 궁금해요. 어디서부터 시작해야 하나요?

**답변** (전폭 문서형, 각주 [1][2][3]는 본문 해당 문장 끝에 위첨자):
> 축복식 준비는 소속 가정 교회를 통한 후보자 등록에서 시작합니다.[1]
>
> 1. **소속 교회와 상의** — 축복을 희망하는 가정은 먼저 소속 교회와 상의합니다.[1]
> 2. **후보자 등록** — 축복 후보자는 소속 교회의 추천을 받아 정해진 기간 안에 등록합니다.[1]
> 3. **준비 교육 이수** — 축복식에 앞서 소정의 준비 교육을 이수합니다.[2]
> 4. **정성 기간** — 축복식에 앞서 각 가정은 정해진 기간의 정성을 준비합니다.[3]
>
> 서류 목록은 교구마다 안내 시기가 달라, 소속 교회 담당자에게 확인하시는 것이 가장 정확합니다.

**인용 목록** ("참고한 자료 2건" — 문서별 그룹, 페이지 표기, 첫 문서에 "주요 근거" 배지):
