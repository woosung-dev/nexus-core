# 블레싱 멀티봇 클라이언트 시안 3종

`docs/prototypes/blessing-nav-r2-2026-08-05/` 의 후속입니다.
브랜드 언어(보라 계열, 골드는 검증된 근거 의미색으로 선 전용), 8화면 구성, 답변 4유형,
어른 연결 순서, 데이터 계약은 그대로 두고 **멀티봇을 정면으로 다뤘습니다.**

`compare.html` 을 열면 세 시안을 같은 상태로 나란히 볼 수 있습니다. 빌드 도구는 필요 없습니다.

## 왜 다시 그렸나

블레싱은 목표가 아니라 **첫 번째 봇**입니다. 이 제품은 RAG 챗봇을 필요에 따라 여러 개 만들어
제공하는 시스템입니다. 그런데 기존 시안 셋은 멀티봇을 의도적으로 미뤘습니다.

- 기준본 `a-register.html:818` 은 봇 5개를 메인 하단 「담당 색인 5권」 **각주**로 내려 두었습니다.
- 세 안 모두 상태 갤러리에 `bots.length === 1` 이면 메인을 건너뛴다고 적어 두었습니다.
- 현재 코드의 멀티봇 UI인 `frontend-client/src/components/landing/BotGrid.tsx` 는
  균일 카드 4열 격자이고, `BotCard.tsx` 는 이미지 + 이름 + 설명 2줄 + 태그만 보여줍니다.
  **봇을 구별해 주지 않습니다.** 이것이 대체 대상입니다.

## 인터뷰에서 정해진 것

| 질문 | 답 | 설계 반영 |
|---|---|---|
| 규모와 묶음 | 평평한 10개 내외 | 조직이 준 그룹 축이 없습니다. **세 안이 각자 다른 축을 스스로 세웠습니다.** |
| 가시성 | 계획 없음. FREE/PRO 형태는 아님 | 가정: 모두 같은 목록을 봅니다. `plan_required` 는 모델에 있으므로 막힌 상태 한 벌만 그렸고, 조직 축으로는 쓰지 않았습니다. 소속별 가시성은 선행 과제 8번입니다. |
| 능력 표기 | **약속으로 미리 적는다** | 사용자 말로만 적습니다. 구현어는 화면에 한 글자도 나오지 않습니다. |

## 세 안이 각각 무엇으로 봇을 구별하나

같은 격자에 스킨만 다르면 실패입니다. 셋은 **멀티봇 명제**가 다릅니다.

| | 명제 | 가르는 축 | 메인의 본문 | 회색조 실루엣 |
|---|---|---|---|---|
| **A 권** | 봇을 고르지 말고 표제어를 골라라 | 표제어 | 통합 색인 29개 + 담당 권 표기. 봇은 뒤의 권 목록 | 좌 긴 목록 + 우 발췌 (밀도 6) |
| **B 접수** | 고르는 화면을 없앤다. 한 줄이 담당을 정한다 | 질문 | 입력 한 줄. 적으면 담당 후보가 규칙선 행으로 자람 | 중앙 1단, 대부분 여백 (밀도 2) |
| **C 총람** | 봇이 아니라 문서에서 출발하라 | 문서 | 승인 문서 14종의 서지. 펼치면 그 문서를 보는 창구 | 전폭 1단 조밀 서지 (밀도 8) |

세 안 모두 색, 별점, 대화 수, 인기순으로 봇을 구별하지 않습니다.
이름과 담당 문서와 능력 표기로만 합니다.

### 규모에서 어디가 무너지나

각 안이 `DESIGN.md` 와 `#states` 화면에 **스스로 무너지는 지점을 적어 두었습니다.**
셋 다 40개에서 좋다고 쓰면 거짓말이기 때문입니다.

| | 1곳 | 3곳 | 14곳 | 40곳 |
|---|---|---|---|---|
| A 권 | 성립 안 함 | 약함 | **가장 잘 맞음** | 성립 (권 목록을 접어야 함) |
| B 접수 | **성립 안 함** | 약함 | 잘 맞음 | **가장 잘 맞음** |
| C 총람 | 성립 | 성립 | 성립 | 성립 (메인이 안 흔들림) |

C 가 규모에는 가장 강하지만 **다른 데서 무너집니다.** 처음 오신 분에게 『가정 생활 규정』 v2.0 은
아무 뜻이 없습니다. 문서 이름을 모르는 사람은 그 화면에서 시작할 수 없습니다.
실무자에게 강하고 당사자에게 약합니다. 이 약점은 설계로 완화할 수 없고, 축 자체가 그렇습니다.

해시로 직접 확인할 수 있습니다. `#home/n0` `#home/n3` `#home/n14` `#home/n40`

## 능력 표기: 기대를 배신하는 쪽만 적는다

운영 원칙 §6 은 내부 분류와 RAG 동작 노출을 금지합니다. 그런데 "이 봇은 기억하지 않습니다"는
구현이 아니라 **사용자와의 약속**입니다. 선을 이렇게 그었습니다.

> **적는 것은 사용자의 기대와 어긋나는 쪽뿐이다. 기대대로면 아무것도 안 적는다.**

| 실제 설정 | 화면 문구 |
|---|---|
| `history_window: 0` | 앞 대화를 이어서 기억하지 않습니다. 질문 하나에 답 하나씩 드립니다. |
| `history_window: > 0` | (안 적음) |
| `evidence_policy_mode: "strict"` | 문서에서 근거를 찾지 못하면 답하지 않습니다. |
| `"legacy"` | (안 적음. 근거 상태는 답변마다 세 라벨로 이미 말합니다) |
| `use_rag: false` | 문서를 근거로 답하지 않습니다. 결론을 대신 내리지 않고 함께 정리하는 쪽입니다. |
| `is_active: false` | 지금은 답하지 않습니다. 같은 내용을 『…』가 이어받았습니다. |
| `plan_required: PRO` | 카드에는 안 적고 **부딪히는 자리에서만** 설명합니다. |

배지를 다 붙이면 목록이 배지 벽이 됩니다. 이 규칙으로 **14곳 중 4곳은 표기가 없습니다.**
화면에 절대 나오지 않는 말: RAG, strict, legacy, history_window, 시스템 프롬프트, 벡터,
검색 엔진, 내부 분류 이름.

## 이관은 답변 5번째 유형이 아니다

답변 4유형은 **질문의 성격**이 가르는 분기입니다. 이관은 질문의 성격이 아니라
**봇의 담당 범위**가 가릅니다. 같은 질문이라도 어느 봇에게 했느냐에 따라 이관이 되기도
안 되기도 합니다. 유형으로 올리면 "질문 성격 → 답변 형태" 계약이 깨집니다.

**「근거 없음」(운영 원칙 §3-D) 의 하위 두 갈래로 두었습니다.**

```
D  문서에서 확인되지 않음
├─ D1  어느 봇도 그 문서를 보지 않는다
│      고정 거절 문장 → 부모님께 여쭐 질문 3개 → 짧은 정서 지지  (기존 그대로)
└─ D2  다른 봇이 그 문서를 본다                                  (이번에 새로 그림)
       담당 봇을 지목 → 왜 그 봇인지를 문서 이름으로 → 옮기기 / 여기서 계속하기
       "질문은 그대로 넘어갑니다. 지금까지의 대화와 근거는 넘어가지 않습니다."
```

세 안이 이 계약을 공유하되 **표현이 다릅니다.**

- **A** 지목한 권의 **카드**
- **B** 메인에서 보던 **접수 행**을 대화 안에 되밈 (이관 = 접수를 한 번 더 하는 것)
- **C** 총람에서 보던 **문서 서지 행**을 대화 안에 그대로 세움

`#thread/handoff` 로 셋을 나란히 볼 수 있습니다.

**D2 는 봇↔문서 연결을 알아야만 성립합니다.** 그 값이 없으면 근거 없이 남의 봇을 지목하게
되므로 **D1 로 떨어뜨리는 것이 정답입니다.** 아래 선행 과제 1번입니다.

## 기술 메모

- 자립형 정적 HTML. 외부 의존은 폰트 CDN 뿐입니다. 엠블럼은 각 파일에 `<symbol>` 로
  인라인해 두었습니다. 인라인해야 `--em-field` / `--em-mark` 로 재채색되기 때문입니다.
- 반응형은 미디어 쿼리가 아니라 **컨테이너 쿼리**입니다. `.app` 이 `container-type: inline-size`
  이고 내부는 `@container app (min-width: …)` 로 반응합니다.
- 프로토타입 크롬은 1100px 미만에서 폭을 돌려주므로 390px 문서에서 앱이 진짜 390px 로 렌더됩니다.
- 노치 폰 목업을 쓰지 않습니다. 좁은 폭에서는 화면 전체를 앱이 씁니다.
- **그라디언트가 한 곳도 없습니다.** 스켈레톤은 단색 펄스, 파선은 `border-style: dashed` 입니다.
  `grep -c gradient` 가 세 파일 모두 0 을 반환합니다.
- **em-dash 가 한 곳도 없습니다.** 코드 주석 포함 0 입니다.
- 모션은 `--motion` 단일 변수로 통제합니다. `animation: none !important` 를 쓰면 OS 에서
  동작 줄이기를 켠 사용자에게 수동 토글이 영구히 먹지 않습니다.
- `window.addEventListener('scroll')` 을 쓰지 않습니다.
- `.screen` 의 표시 여부는 `[data-on]` 하나가 정합니다. 다른 클래스에서 `display` 를 선언하면
  숨겨야 할 화면이 함께 렌더됩니다(작업 중 실제로 났던 버그입니다).

# 코드에 옮기기 전에 필요한 것 (백엔드 선행 과제)

세 시안이 그렸지만 지금 API 로는 값을 채울 수 없는 것들입니다.
번호는 급한 순서입니다.

### 1. 봇 ↔ 문서(코퍼스) 연결 — 없음

**봇을 구별하는 가장 중요한 축인데 클라이언트가 알 수 없습니다.**
`Bot` 모델에도 `BotResponse` 에도 담당 문서 목록이 없습니다.

여기에 걸려 있는 것: A안의 통합 색인, B안의 담당 배정, C안의 총람 **전체**,
세 안의 봇 상세 대조 블록, 그리고 이관(D2). 특히 C안은 메인이 이 값의 역산이라
이 값이 없으면 화면 자체가 성립하지 않습니다.

없으면 D2 는 D1 으로 떨어뜨려야 합니다. 근거 없이 남의 봇을 지목하는 것이
문서명을 지어내는 것과 같은 종류의 거짓말이기 때문입니다.

### 2. "이 질문은 어느 봇 담당인가" 의 판단 근거 — 없음

B안의 심장입니다. 지금 그릴 수 있는 최대치는 **이름·태그·낱말 문자열 매칭**이고,
그것은 근거가 아닙니다. B안은 그 사실을 숨기지 않고 화면에 그대로 적습니다.

> 이 순서는 문서에 그 낱말이 있는지로만 정했습니다.

백엔드가 판단 근거를 주기 전까지 B안은 절반만 진짜입니다.

### 3. `use_rag` 가 `BotResponse` 에 없음

`backend/app/models/bot.py:43` 에는 있는데 `backend/app/schemas/bot.py` 의 `BotResponse`
에는 빠져 있습니다. "문서를 근거로 답하지 않습니다" 표기를 그리려면 응답에 실어야 합니다.
`BotCreateRequest` 에도 없어서 관리자도 생성 시에는 못 정합니다.

### 4. `updated_at` 이 `BotResponse` 에 없음

`models/bot.py:58` 에는 있습니다. "언제 갱신됐는지"를 큰 활자에 넣는 기준본 원칙이
실 데이터로는 못 채워집니다. 세 안 모두 이 값을 예시로 채워 두었습니다.

### 5. 클라이언트 타입이 실제 응답보다 좁음

`frontend-client/src/types/api.ts:10` 의 `BotResponse` 에
`is_active` · `history_window` · `evidence_policy_mode` 가 빠져 있습니다.
**서버는 이미 보내고 있으므로 타입만 넓히면 능력 표기 3종 중 2종은 바로 채워집니다.**
가장 싸게 얻을 수 있는 항목입니다.

### 6. `BotResponse` 가 `system_prompt` 를 공개 엔드포인트로 내보냄

`backend/app/api/v1/endpoints/bots.py:18` 의 목록 엔드포인트가 `BotResponse` 를 쓰고,
그 스키마에 `system_prompt` 가 들어 있습니다. **운영 원칙 §6 위반입니다.**
시안과 무관하게 별건으로 잘라내야 합니다.

### 7. 봇 그룹 / 카테고리 — 없음

그래서 세 안이 각자 축을 만들었습니다. 조직이 그룹 축을 정하면 세 안 모두
그 축을 2차 정렬로 받아들일 수 있는 구조입니다.

### 8. 소속별 봇 가시성 — 미정

인터뷰에서 "계획 없음, 미래에 자유롭게, FREE/PRO 형태는 아님" 으로 답을 받았습니다.
세 안 모두 "모두 같은 목록" 가정으로 그렸고, 목록을 걸러 주는 층이 나중에 끼어들 수 있게
데이터 진입점(`visibleBots()`)을 한 곳으로 모아 두었습니다.

### 9. (r2 에서 이월) 인용 대기 상태

`ChatProvider.tsx` 의 백필 폴링(2초 × 15회, 실측 약 15초)에 진행 상태가 노출되지 않습니다.
컨텍스트가 내보내는 값에 폴링 여부가 없어 바인딩할 변수가 없습니다.
세 안 모두 「확인 중」 상태를 그려 두었습니다.

### 10. (r2 에서 이월) 검색되었지만 인용되지 않은 문서 목록

`Citation[]` 에는 인용된 것만 옵니다. 인용 0건과 검색 실패를 화면에서 구분하려면
백엔드가 검색 결과 목록을 함께 보내야 합니다.

### 11. (r2 에서 이월) 프런트 기본값 정리

`frontend-client/src/app/globals.css` 의 `--primary` 가 아직 앰버이고,
`layout.tsx` 가 Geist 만 로드해 한글이 시스템 폴백으로 떨어집니다.
`.dark` 블록은 라이트 값을 복사하고 있습니다. 어느 안을 고르든 이 셋은 먼저 정리해야 합니다.
