# 설계 (미구현) — 원본 문서가 개정될 때 위키를 어떻게 갱신하나

> **상태: 아직 안 만들었다.** 지금은 갱신 경로 자체가 없다 —
> `_split.py` 가 sha256 불일치로 즉시 중단한다.
>
> 선행 문서: `handoff-llm-wiki-2026-08-07.md` (설계 정본) ·
> 루트 `AGENTS.md` (저장소 규약)

---

## 0. 30초 요약

규정집은 개정이 본업이다. v19→v20 에서 **제38조 하나가 신설되자 그 뒤 62개 조문 번호가 +1 밀렸다.**
지금 위키의 `reg` 앵커 800회 중 **561회(70%)가 제38조 이상**이라, 조문 하나만 끼워 넣어도
인용의 70%가 어긋난다.

다행히 **조용히 오염되지는 않는다** — `_verify.py` 의 인용 대조가 시끄럽게 터진다.
그래서 갱신 설계의 요지는 *"무엇이 바뀌었는지 따로 계산하지 않고, `_verify.py` 를 변경 감지기로 쓴다"* 는 것이다.

**지금 당장 필요하지는 않다.** 관리자가 모순을 판정해 저장하기 시작하는 순간부터 필수가 된다.

## 1. 왜 이게 문제인가 — 실측

```
v19 → v20 :  그대로 37개 · +1 밀림 62개 · 미매칭 0개
             제38조(축복자녀 간 축복) 신설 →
             제38조~제99조가 전부 제39조~제100조로 이동

현재 위키   :  reg 앵커 800회 · 이 중 제38조 이상 561회 (70%)
```

`[[src: reg-43]]` 은 **위치 기반 식별자**다. 문서가 개정되면 같은 이름이 다른 조문을 가리킨다.

---

## 2. 카파시 llm-wiki 는 이 경우를 정의하지 않는다

원문(<https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f>)을 확인했다.
3동작(Ingest / Query / Lint) 중 Lint 에 이 줄이 있을 뿐이다.

> "Look for: contradictions between pages, **stale claims that newer sources have superseded**,
> orphan pages with no inbound links"

**감지**만 말하고 **절차**는 없다. 소스가 계속 *추가*되는 상황을 가정한 패턴이지,
같은 소스가 *개정*되는 상황은 다루지 않는다. 규정 도메인에 특유한 부분이라 우리가 설계한다.

---

## 3. 바뀜의 4종류와 위험도

| 종류 | 위키에 무슨 일이 | 검출되나 | 대응 |
|---|---|---|---|
| **내용만 수정** (번호 그대로) | 인용이 원문에 없어짐 | `_verify.py` 인용 대조 | 그 조문만 재ingest |
| **조문 추가** | 위키가 새 조문을 모름 | 커버리지 검사 | 그 조문만 ingest |
| **조문 삭제** | 앵커가 없는 소스를 가리킴 | 앵커 존재 검사 | **사람 판단** (자동 삭제 금지) |
| **번호 밀림** | 앵커가 다른 조문을 가리킴 | 인용 대조가 터짐 | 앵커 재배치 |

**네 종류 모두 조용히 통과하지 않는다.** "모든 문장에 인용을 붙여라"를 강제한 값을 여기서 회수한다.

한계: 프로그램은 *"인용이 안 맞는다"* 까지만 안다.
**"내용이 바뀐 건지, 번호만 밀린 건지"는 구분하지 못한다.** 그 구분이 이 설계의 전부다.

## 4. 채택안 — 이동 재배치 + 바뀐 것만 재ingest

```
1. 새 PDF → _split.py → sources/<새 sha8>/        ← 옛 판은 지우지 않는다
2. 표제 대조로 이동표 생성                          ← _corpus_build.py:build_shift_map() 재사용
     "제43조(12일 가정출발의식)" 이 새 판에서 제44조 → reg-43 → reg-44
3. 위키 앵커를 기계적으로 재배치                     ← LLM 안 씀. 결정적.
4. _verify.py 전수 재실행                          ← 여기가 변경 감지기다
     인용 통과 = 그 조문은 실질적으로 안 바뀜 → 손 안 댐
     인용 실패 = 그 조문 내용이 바뀜         → 재ingest 대상
5. 삭제된 조문 → 그 앵커를 쓰는 문장을 「검토 필요」 표시 (자동 삭제 금지)
   신설 조문   → 그것만 ingest
6. Lint 한 바퀴 — 모순·낡은 주장 재점검
```

**비용:** v19→v20 급 개정이면 62개 밀림 + 1개 신설 → 실제 재ingest 는 1~5건, 10분 이내.
전량 재실행(6.6시간)이 10분이 된다.

### 왜 전량 재실행(A안)이 아닌가

1. **관리자 판정이 전부 날아간다.** 모순을 검토해 "이게 현행"이라고 눌러둔 것이 사라진다.
2. **비결정적이다.** 같은 입력으로도 페이지 이름·분할이 달라진다.
   138쪽이 다음엔 130쪽일 수 있고, 슬러그가 바뀌면 교차참조가 깨진다.
3. 안 바뀐 조문까지 전부 다시 돈다.

### 왜 "LLM에게 뭐가 바뀌었는지 묻기"(B안)가 아닌가

표제 대조와 해시로 **결정적으로** 알 수 있는 것을 LLM 에 맡기는 것이다. 느리고 틀린다.

## 5. 구현해야 할 것 3개

| # | 무엇 | 근거 |
|---|---|---|
| 1 | **앵커 재배치 스크립트** — `build_shift_map` 출력으로 위키 앵커 일괄 치환 | 반나절 |
| 2 | **관리자 판정 보존 규칙** — 재ingest 가 사람의 판단을 덮어쓰지 않게 | 선례: `golden_2026-08/_load.py` (`status != '초안' 이면 건너뜀`) |
| 3 | **판 표시** — 문장마다 "이 인용은 v20 기준"이 남아야 한다 | `sources/<sha8>/` 로 판이 갈리므로 앵커에 sha8 을 붙이면 된다 |

## 6. 함정

- **옛 판 `sources/<sha8>/` 를 지우지 마라.** 지우면 "이 문장은 어느 판 기준이었나"를 못 되짚는다.
  `manifest.json` 이 현재 판을 가리키게 하고 옛 판은 남긴다.
- **삭제된 조문의 문장을 자동으로 지우지 마라.** 규정이 사라진 것과 다른 조문으로 옮겨간 것을
  프로그램은 구분 못 한다. 「검토 필요」로 세워 두고 사람이 본다.
- **표제가 바뀐 채 이동한 조문은 이동표에 안 잡힌다.** `build_shift_map` 은 표제 완전일치로 맞춘다.
  v19→v20 에서는 미매칭 0개였지만 항상 그러리라는 보장은 없다.
- **재배치와 재ingest 사이에 화면을 열지 마라.** 앵커만 옮기고 인용 검증 전인 중간 상태다.

---

## 7. 이 설계를 미루는 근거

지금 위키는 **아무도 쓰지 않는다** — 백엔드에 `wiki` 참조 0건이고 챗봇 경로에 없다.
규정집이 v21 로 바뀌면 그냥 6.6시간 다시 돌리면 되고 잃을 것이 없다.

**필수가 되는 시점:** 관리자가 모순을 검토해 판정을 DB 에 저장하기 시작할 때.
그때부터 재실행이 사람의 판단을 지우기 때문이다.
