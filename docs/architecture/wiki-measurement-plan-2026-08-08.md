# 위키 3안 측정 계획 — 정답지 0806 기준

> 2026-08-08. 입력: `~/Downloads/축복 챗봇 정답지 요청 0806.xlsx` (관리자 회신본).
> 목적: 3안(위키 → 원문 직접 주입)이 값어치가 있는지 **접을 수 있는 형태로** 잰다.

## 1. 회신 상태 — 뭐가 왔나

| 시트 | 요청 | 회신 | 쓸 수 있나 |
|---|---|---|---|
| ① 45문항 정답 | 45 | **10건** (근거 6건) | 부분 |
| ② 꼭 필요한 3가지 | 3 | **1건** — 정답기준 = **v20** 확정 | 예 |
| ③ 갈린 18건 | 18 | 0 | 아니오 |
| ④ 판정 규칙 | 6 | 0 | 아니오 |
| ⑤ 필수 키워드 구분 | 45 | 0 | — |
| ⑥ 추가 시나리오 | 4유형 | 0 | 아니오 |

**⑤ 시트에 이미 들어 있는 것이 정답 10건보다 값집니다.**

```
45문항 전체 키워드      문항당 평균 6.8개 (최소 4 · 최대 13)
현재 충족률 baseline    평균 67.1% · 중앙 67% · 0%인 문항 1건 · 100%인 문항 0건
위험도                  상 28 · 중 10 · 하 1 · 없음 6
카테고리                순결·안전 7 / 축복의미 6 / 준비·자격 6 / 가정출발 6 / 유형 5 …
```

즉 **45문항 전체에 대해 기계 채점이 가능한 자와 기준선이 이미 있습니다.**

## 2. 지금 잴 수 있는 것과 없는 것

### 못 잽니다 — 답변 품질 절대평가

정답 10건으로는 승패를 못 가립니다. 판정선 20pp 에서 10문항이면 **2문항 차이**입니다. 잡음입니다.

### 잽니다 — A/B 상대비교 45문항 전체

키워드 루브릭이 엄격한 것(관리자가 적은 키워드를 전부 필수로 셈)은 **A/B 에서는 문제가 아닙니다.**
양쪽 팔이 같은 자를 씁니다. 절대 점수는 못 믿어도 **차이는 믿을 수 있습니다.**

### 가장 중요한 건 정답 없이도 잽니다 — 1단 라우팅

3안의 최대 위험은 "1단이 틀리면 2단이 아무리 좋아도 못 고친다"입니다.
이건 답변을 만들지 않고도 잽니다. **먼저 이것부터 잽니다.**

## 3. 측정 설계 — 4층

### 층 0 — 커버리지 사전 분류 (2시간 · 과금 0)

비교를 오염시키는 문항을 먼저 걷어냅니다.

45문항을 셋으로 가릅니다.

```
A. 위키가 다루는 것          → 3안이 이길 수 있는 구간
B. 원문에는 있는데 위키에 없는 것 → 폴백이 받아야 하는 구간
C. 어느 문서에도 없는 것       → 어떤 안으로도 못 맞힘. 비교에서 제외
```

**C 를 안 걷어내면 두 팔이 똑같이 틀리고 차이가 희석됩니다.**

이미 확인된 C 사례: **#13 「미성년자도 축복을 받을 수 있어?」의 정답 근거가
`부모매칭가이드북`** 입니다. 챗봇이 갖고 있지 않은 문서입니다.
(②-2 「챗봇이 갖고 있어야 할 공문 목록」이 빈칸으로 온 것과 같은 뿌리입니다.)

산출물: `exports/wiki_eval/coverage.json` — 문항별 A/B/C + 근거

### 층 1 — 라우팅만 (반나절 · 임베딩 183회 ≈ 0.01달러)

**답변을 만들지 않습니다.** 위키가 옳은 원문을 소환하는지만 봅니다.

```
45문항 각각
 └─▶ 위키 138쪽 「## 요약」 임베딩과 대조 → top-3 페이지
       └─▶ 세 쪽의 frontmatter sources 합집합 = 소환된 원문 앵커 집합
             ├─ 정답 근거가 있는 6건  → 그 조문이 집합 안에 있나        (직접 검증)
             └─ 나머지 39건          → ⑤ 키워드가 소환 원문 안에 있나  (근사 검증)
```

| 지표 | 뜻 |
|---|---|
| **근거 소환률** | 정답 근거 조문이 top-3 sources 안에 들어온 비율 |
| **키워드 포함률** | ⑤ 키워드가 소환된 원문 본문에 등장하는 비율 |
| 유사도 분포 | A군과 C군의 1단 유사도가 갈리는가 — **폴백 문턱값이 여기서 나옴** |

**판정선 — 근거 소환률이 80% 미만이면 3안을 접습니다.**
1단이 못 찾는 것을 2단이 만들어낼 수는 없습니다. 여기서 접으면 층 2 비용이 0이 됩니다.

산출물: `exports/wiki_eval/stage1.json` + 관리자 화면 표

### 층 2 — 답변 A/B (하루 · 270 호출)

층 1을 통과했을 때만 합니다.

```
팔 A   현행 file_search 그대로            ← baseline. 키워드 충족률 67.1%
팔 B   3-B  위키 → 원문 직접 주입          ← 검색 호출 0
팔 C   병렬 기록 — 합치지 않고 나란히 저장   ← 문턱값 근거 수집용

45문항 × 3팔 × 2회 = 270 호출
2회 돌리는 이유: 같은 조건 재현성. 프롬프트4 실험에서 팔 간 차이 8pp가
잡음 바닥 20pp 안이었다 — 잡음을 먼저 재야 차이를 믿을 수 있다.
```

**채점 2종**

| | 무엇 | 대상 |
|---|---|---|
| 기계 | ⑤ 키워드 충족률 | 45문항 전부 |
| LLM-judge | 정답 10건과 대조 | 10문항 (codex CLI — 과금 회피) |

**판정선 — 키워드 충족률이 팔 A 대비 +20pp 미만이면 3안은 값어치가 없습니다.**

부가 지표: 응답 지연(3-B는 file_search 호출이 없어 줄어야 함) · 인용 건수 ·
「확인되지 않습니다」 유보율.

### 층 3 — 정답지 확장 후 본 측정

나머지 35건과 ④ 판정 규칙이 오면 같은 하네스를 그대로 다시 돌립니다.
층 2 산출물을 그대로 재활용합니다.

## 5. 세팅 — 필요한 것

### 확인만 하면 되는 것

1. **봇 11의 file_search 스토어에 원문이 실제로 올라가 있는지.**
   팔 A(baseline)를 못 돌리면 비교 자체가 성립하지 않습니다.
   → `list_documents(bot_id=11)` 로 확인. 비어 있으면 재업로드가 선행입니다.
2. **로컬 `.env` 의 `GEMINI_API_KEY` 가 살아 있는지.** 임베딩과 생성 둘 다 씁니다.
3. **`DATABASE_URL` 이 어느 쪽을 보는지** — Neon(라이브) vs localhost(개발).
   측정은 **읽기 전용**이라 Neon 직결로 충분합니다. 쓰기는 `exports/` 파일로만 합니다.

### 과금 예상


층 2의 LLM-judge 는 codex CLI 로 돌립니다(구독 사용, 추가 과금 없음).

## 6. 관리자에게 재요청 — 우선순위를 뒤집습니다

정답 35건보다 **④ 판정 규칙 6개가 급합니다.** 문항 하나가 아니라 **45문항 전체의 채점을 바꿉니다.**

| 순위 | 항목 | 왜 급한가 | 관리자 부담 |
|---|---|---|---|
| 1 | **④-6 조문번호를 답변에 실어도 되는가** | 3안의 출력 형식이 여기 달림. v20이 승인 전 초안이라 대외 인용 금지일 수 있음 | 셋 중 하나 고르기 |
| 2 | **④-3 「확인되지 않습니다」 기본 규칙 확인** | 유보를 정답으로 셀지가 45문항 전체 채점을 바꿈 | O/X |
| 3 | **②-1 폐지·현행 미적용 목록** | C05·C06 구간이 지금 8/8 오답. 어느 안으로도 못 고침 | 목록 |
| 4 | ④-4 가정행복국 대표번호 | 프롬프트 두 개의 번호가 서로 다름 | 번호 하나 |
| 5 | ①의 나머지 35건 정답 | 본 측정용 | 큼 |

**1~4번은 합쳐서 10분이면 됩니다.** 35건 정답을 기다리는 동안 이것부터 받으면
층 2를 제대로 채점할 수 있습니다.
