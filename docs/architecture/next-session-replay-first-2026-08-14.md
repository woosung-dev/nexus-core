### 인용 형식 지시 — **채택하고 라이브 반영 완료**

`[출력 형식]` 의 「규정 근거를 밝힐 수 있으면 함께 언급합니다」 한 줄을 두 줄로 교체했다.

### ⚠ 이 변경으로 알게 된 것 — **인용 표기가 이제 세 겹이다**

사용자 화면에는 원래도 출처가 나가고 있었다.

| 기전 | 어디서 오나 | 조건 |
|---|---|---|
| **자료 카드**(문서명·스니펫·형광펜) | `wiki/service.py:_citations()` — 주입 유닛마다 자동 생성 | 어휘 경로 **평균 4.4건, 사실상 항상** |
| **본문 각주 `[1]`** | `citationMarkers.ts` — `segments`(근거 구절)에 앵커 | 배경 백필이 채워야 붙는다 |
| **본문 `(근거: 제41조)`** ← 이번에 추가 | 모델이 직접 씀 | 게이트가 읽는 유일한 것 |

**세 번째가 필요한 이유는 오직 게이트 때문이다.** 자료 카드는 주입만 하면 무조건 생겨서
「모델이 그 원문을 실제로 썼는가」를 증명하지 못한다(#59 가 고친 함정).

즉 **화면 중복을 감수하고 게이트 통과율을 산 것**이다. 근본 해결은 게이트가 본문 표기를
요구하지 않고도 근거 사용을 검증하는 것인데, 「어휘 매칭으로 판정」은 **3전 3패** 이력이 있다.
다음에 손대려면 그 이력부터 읽어라.

## 3. STEP 3 — 과거 질문 replay (이번 세션의 본체)

**목적은 A/B 가 아니다.** 「무엇을 못 답하나」를 추측이 아니라 **목록**으로 만드는 것이다.
그 목록이 있어야 관리자에게 「자료 주세요」를 감이 아니라 숫자로 요구할 수 있다.

### 3-1. 입력 — **이미 만들어 뒀다**

```
exports/replay_2026-08/_input.json       반복 2회 이상 600건  ← 여기부터 돈다
exports/replay_2026-08/_input_all.json   고유 전체 1,183건
```

라이브 `messages(role=user)` 를 정규화해 고유화한 것이다. `k` = 같은 질문이 반복된 횟수,
`cid` = `R0001…`(빈도 내림차순). 상위 몇 건:

```
R0001 14회  축복은 왜 받아야 해요?
R0002 12회  축복가기까지의 과정을 자세히 알려줘. 신청서, 준비물, 일정 모두 포함해서…
R0003  7회  교류중 상대에게 "사랑해"라는 애정표현을 하는건 피해야할 행동일까?
```

### 3-2. 하네스 — `--questions` **이미 넣어 뒀다**

```bash
cd backend && .venv/bin/python -u ../exports/regression/_run_e2e.py \
  --bot-id 29 --tag replay_0815 --questions ../exports/replay_2026-08/_input.json \
  --reps 1 --throttle 10 --retrieval-mode lexical --policy strict
```

식별자가 빈 문항이 있으면 하네스가 **시작 전에 거부한다**(resume 이 뭉개지므로).
**라이브에서 읽고 로컬 봇 29 로 돌린다.** 라이브에 세션·메시지를 쓰지 마라.

- `--reps 1` 이면 된다. 재현성 측정이 아니라 **결손 수집**이다
- `--policy strict` — 라이브와 같은 조건이어야 「무엇을 못 답하나」가 맞는다
- **호출 600회.** 무료 키는 모델당 하루 500회(KST 16:00 리셋)라 **이틀에 나눠 돌거나 유료 키가 필요하다.**
  태그를 그대로 쓰면 resume 된다
- `--throttle 10` 미만 금지 — 배경 호출로 요청률이 2배가 되어 429(분당 제한)를 맞는다

### 3-3. 분류 — `triage` 4값

`unanswered_questions` 에 쌓인 것을 4값으로 가른다.

| triage | 뜻 | 다음 행동 |
|---|---|---|
| `문서없음` | 규정집이 그 쟁점을 안 다룬다 | **관리자에게 자료 요청** ← 3차 요청서에 합류 |
| `검색못함` | 문서에는 있는데 검색이 못 뽑았다 | 검색기 개선 |
| `문서오류` | 문서가 틀렸다 | `ops_facts` 로 덮는다 |
| `해당없음` | 규정 밖 질문 | 응대 문구 |

**`문서없음` 과 `검색못함` 을 가르는 것이 이 단계의 전부다.** 둘을 섞으면 관리자에게
「자료 주세요」를 하면서 실은 우리 검색이 문제인 경우가 끼어든다.

가르는 법: 답을 못 한 질문의 키워드로 **코퍼스 250유닛을 직접 grep** 한다. 원문에 있으면 `검색못함`,
없으면 `문서없음`. LLM 판정 말고 문자열 매칭으로 해라 — 검색 점수로 판정하는 것은 **3전 3패**다.

### 3-4. 산출물

```
exports/replay_2026-08/_input.json      입력 600건
```

## 4. STEP 4 — 관리자 1회 집중 요청

관리자는 **저대역폭이다.** 1차·2차가 미회신이거나 부분 회신이었다. 그러니 **한 번에, 숫자로.**

3차 요청서가 이미 작성돼 있다 → `exports/admin_request_2026-08-14/요청서_3차_2026-08-14.md`

**replay 결과를 그 문서에 합류시켜라.** 지금 요청서는 45문항 기준이라 「8건이 문서에 없다」인데,
replay 를 돌리면 **실사용자가 실제로 물은 것 중 몇 건이 문서 결손인지**가 나온다. 그게 훨씬 세다.

추가할 섹션:

```
## 실제 사용자 질문 N건 중 M건을 문서가 없어 답하지 못합니다

| 빈도 | 질문 | 왜 못 답하나 |
|---:|---|---|
| 14회 | ... | 규정집에 해당 조문 없음 |
...
```

**보내기 전에 확인**: 이 문서는 사용자가 보낸다. 내가 임의로 발송하지 않는다.
