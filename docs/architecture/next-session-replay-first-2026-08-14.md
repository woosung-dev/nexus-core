## 3. STEP 3 — 과거 질문 replay (이번 세션의 본체)

**목적은 A/B 가 아니다.** 「무엇을 못 답하나」를 추측이 아니라 **목록**으로 만드는 것이다.
그 목록이 있어야 관리자에게 「자료 주세요」를 감이 아니라 숫자로 요구할 수 있다.

### 3-1. 대상 뽑기 (읽기 전용)

```sql
-- 2회 이상 반복된 질문 600건. 여기부터 돈다
with u as (
  select lower(regexp_replace(content,'[[:space:][:punct:]]','','g')) n,
         min(content) q, count(*) k
  from messages where role='user' group by 1)
select q, k from u
where k >= 2 and length(q) between 6 and 300
order by k desc, q;
```

**라이브에서 읽고, 로컬 봇 29 로 돌린다.** 라이브에 세션·메시지를 쓰지 마라.

### 3-2. 하네스

`_run_e2e.py` 는 `questions.json` 을 하드코딩으로 읽는다. **replay 용 입력 파일을 받게 고쳐야 한다** —
`--questions <path>` 인자 하나 추가가 가장 작다. 형식은 `{"items":[{"q": "...", "cid": "R0001", ...}]}`.

`cid` 를 반드시 채워라 — resume 키가 `(cid or gid, rep)` 라서 비면 뭉개진다(앞 세션에서 고친 함정).

```bash
cd backend && .venv/bin/python -u ../exports/regression/_run_e2e.py \
  --bot-id 29 --tag replay_0815 --questions ../exports/replay_2026-08/_input.json \
  --reps 1 --throttle 10 --retrieval-mode lexical --policy strict
```

- `--reps 1` 이면 된다. 재현성 측정이 아니라 **결손 수집**이다
- `--policy strict` — 라이브와 같은 조건이어야 「무엇을 못 답하나」가 맞는다
- **호출 600회.** 무료 키는 모델당 하루 500회(KST 16:00 리셋)라 **이틀에 나눠 돌거나 유료 키가 필요하다.**
  태그를 그대로 쓰면 resume 된다
- `--throttle 10` 미만 금지 — 배경 호출로 요청률이 2배가 되어 429(분당 제한)를 맞는다

### 3-3. 분류 — `triage` 4값

`unanswered_questions` 에 쌓인 것을 4값으로 가른다.

| triage | 뜻 | 다음 행동 |
|---|---|---|
| `문서없음` | 규정집이 그 쟁점을 안 다룬다 | **관리자에게 자료 요청** ← 3차 요청서에 합류 |
| `검색못함` | 문서에는 있는데 검색이 못 뽑았다 | 검색기 개선 |
| `문서오류` | 문서가 틀렸다 | `ops_facts` 로 덮는다 |
| `해당없음` | 규정 밖 질문 | 응대 문구 |

**`문서없음` 과 `검색못함` 을 가르는 것이 이 단계의 전부다.** 둘을 섞으면 관리자에게
「자료 주세요」를 하면서 실은 우리 검색이 문제인 경우가 끼어든다.

가르는 법: 답을 못 한 질문의 키워드로 **코퍼스 250유닛을 직접 grep** 한다. 원문에 있으면 `검색못함`,
없으면 `문서없음`. LLM 판정 말고 문자열 매칭으로 해라 — 검색 점수로 판정하는 것은 **3전 3패**다.

### 3-4. 산출물

```

exports/regression/_e2e_replay_0815.json  응답 + trace
exports/replay_2026-08/FINDINGS.md      결손 목록 (triage 4값 · 빈도순)
```

**빈도순으로 정렬하라.** 「14번 물어본 질문에 답을 못 한다」와 「1번 물어본 질문」은 우선순위가 다르다.

## 4. STEP 4 — 관리자 1회 집중 요청

관리자는 **저대역폭이다.** 1차·2차가 미회신이거나 부분 회신이었다. 그러니 **한 번에, 숫자로.**

3차 요청서가 이미 작성돼 있다 → `exports/admin_request_2026-08-14/요청서_3차_2026-08-14.md`

**replay 결과를 그 문서에 합류시켜라.** 지금 요청서는 45문항 기준이라 「8건이 문서에 없다」인데,
replay 를 돌리면 **실사용자가 실제로 물은 것 중 몇 건이 문서 결손인지**가 나온다. 그게 훨씬 세다.

추가할 섹션:

```
## 실제 사용자 질문 N건 중 M건을 문서가 없어 답하지 못합니다

| 빈도 | 질문 | 왜 못 답하나 |
|---:|---|---|
| 14회 | ... | 규정집에 해당 조문 없음 |
...
```

**보내기 전에 확인**: 이 문서는 사용자가 보낸다. 내가 임의로 발송하지 않는다.

## 5. KPI 재계산 스크립트 (호출 0회)

앞 세션에서 쓴 것. `s1_lex_0813` · `cite_0814` 등 어느 태그든 잰다.

- 문서상태는 `exports/golden45_2026-08-11/_golden_vs_docs.json` 의 `rows[].verdict` 에 있고,
  **키는 `questions.json` 의 `no`(1~45)** 다. `gid`·`cid` 가 아니다 — 여기서 한 번 헤맸다
- C01~C10 은 `no` 가 없다. `bucket == 'C'` → `함정` 으로 넣는다
- 게이트 재현은 `evidence_ok` = ①주입 근거를 짚었나 **∧** ②지어낸 게 없나. ① 만 재현하면 13.7pp 낮게 나온다
- 검산: `s1_lex_0813` 의 전체 유보가 **68.2%(75/110)** 로 나와야 앞 문서 §0-5 와 맞는다

**§1 KPI 현재값 (배포된 게이트 · 어휘 110셀)**

| 지표 | 목표 | 현재 |
|---|---|---:|
| ① 유해 확답 | 0건 | **0건** ✅ |
| ② 유보율(문서없음) | ≥95% | **87.5%** (14/16) |
| ③ 과잉 거절 | ≤5% | **30.3%** (20/66) ❌ |

> ⚠ **문서 두 조항이 서로 어긋난다.** §1 은 과잉 거절 ≤5% 를 반영 기준으로 걸었고,
> §0-5 는 게이트를 ①∪② 로 바꾸며 「과잉 차단을 의도적으로 감수」했다(유보 68.2%).
> **우리는 §1 기준을 못 맞춘 채 라이브에 켰다.** 사용자 결정이었으나 기준 미달인 것은 사실이다.
