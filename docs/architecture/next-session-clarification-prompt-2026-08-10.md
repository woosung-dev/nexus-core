## 목표

사용자 질문에 근거가 부족할 때 챗봇이 **그럴듯한 답을 지어내지 않고 되묻게** 만든다.

지금은 되묻지 않는다. 45문항 실측에서 현재 기본값 `file_search` 는 45문항 **전부**에서
무언가를 주장했고 그중 14.2%가 규정 원문에 근거가 없었다. 모를 때 모른다고 말하지 않는 것이
이 제품의 가장 큰 결함이다.

## 이 세션이 끝났을 때 있어야 할 것

1. **결정적 재질문 트리거** — 검색 점수 임계값 기반. `lexical` 검색이 반환하는
   `Retrieved.top_score` / `ranked_units` 를 읽어 「근거 부족」을 판정한다.
2. **임계값의 근거** — 45문항 코퍼스로 임계값을 스윕해서, 어디를 자르면 무주장 6건을
   잡으면서 정상 답변을 몇 건 희생하는지 표로 낸다. 임의로 고른 숫자는 받아들이지 않는다.
3. **소규모 실측** — 트리거가 걸린 질문에 대해 되물은 뒤 받은 답으로 다시 답했을 때
   지어냄율이 실제로 내려가는지 측정한다. 전체 45문항일 필요 없다. 트리거가 걸리는
   문항만으로 충분하다.
4. **판단 기록** — 무엇을 재고 무엇을 결정했는지 `docs/architecture/` 에 남긴다.
   대화 요약이 아니라 검증된 사실과 확인 명령의 목록으로 쓴다.

## 제약 — 이유와 함께

**LLM 에게 "되물을까 말까"를 묻지 마라.** PR #51 이 정확히 그 방식으로 실패했다
(60문항 중 30건 경로 불일치, 클로즈). 판정은 검색 점수라는 결정적 신호에서 나와야 한다.
LLM 은 「무엇을 되물을지」 문장을 만드는 데만 쓴다 — 그건 이미 `clarification_service.py` 가 한다.

**재질문 레이어를 새로 만들지 마라.** PR #50 이 837줄짜리 `clarification_service.py`,
정책 스키마(`required_slots`, `when_unknown: ask|handoff|allow_answer`), 관리자 화면,
클라이언트 UI, 테스트 22개를 이미 만들어 뒀다. 없는 것은 「언제 되물을지」 신호 하나뿐이다.
기존 코드를 읽고 거기에 붙여라.

**`file_search` 위에서는 만들 수 없다.** Gemini File Search 는 relevance score 를 반환하지
않는다(`grep -rn "score" backend/app/services/rag/*.py` → 0건). 임계값을 잡으려면
`lexical` 이어야 한다. 이 트랙은 `lexical` 전환과 같은 방향이고, 그게 실행 순서 1번이다.

**측정 지표는 재질문 발생률이 아니다.** 업계 연구("Clarification Is Not Enough")가 지적한
병목은 「되물어 받은 답으로 제대로 답하는가」다. 되묻기만 늘고 답이 그대로면 실패다.

**7개 종착 경로를 확인하라.** `chat_service.process_chat_request` 는 7군데에서 반환한다
(347/393/410/483/503/514/551). 한 곳만 고치면 나머지 6개로 새어나간다.
`lexical` 은 스트리밍이 안 되므로(`stream_ok` 게이트, 390행) 재질문 UX 는 비스트리밍 전제다.

**라이브 DB 에 쓰지 마라.** 확인이 필요하면 읽기만 하고, 쓰기가 필요하면 나에게 먼저 물어라.
`backend/.env` 9~11행에 Neon 자격증명이 있다 — 커밋하지 마라.

**측정 하네스를 재실행할 때 `--retry-failed` 를 붙여라.** 성공한 셀을 다시 부르면 답변이
새로 생성돼 앞서 감사한 결과와 어긋난다.

## 열려 있는 것 — 네가 정하라

- 임계값을 페이지 공간 점수로 잡을지 유닛 공간 점수로 잡을지 (RRF 가 두 번 돈다)
- 단일 임계값인지 2단(항상 묻기 / 가끔 묻기 / 조용히 답하기)인지
  — "Clarify Once, Learn the Default" 는 0.60 / 0.85 2단을 권한다
- 확정된 기본값을 `ops_facts` 에 넣을지 (구조가 같다. 지금 0행이다)
- 봇별 on/off 를 `clarify_enabled` 로 할지 새 컬럼으로 할지

정하기 전에 근거를 대라. 근거 없이 고른 설계는 다시 뜯게 된다.

## 작업 방식

첫 응답에서 계획을 길게 쓰지 마라. 읽어야 할 코드를 읽고, 잴 수 있는 것부터 재라.

요청한 범위를 그대로 전달하라. 애매한 부분은 신중한 동료가 하듯 판단하고, 해석에 따라
결과물이 크게 달라지는 경우에만 물어라. 요청이 잘못됐다고 판단하면 한두 문장으로 말한 뒤
가정을 명시하고 계속 진행하라. 요청이 함의하지 않는 변경까지 손대지는 마라.

응답은 결론부터. 처음 한 문장이 "무슨 일이 있었나 / 무엇을 찾았나"에 답해야 한다.
근거와 설명은 그 뒤에. 짧게 쓰려고 축약어·화살표 사슬·전문용어로 압축하지 말고,
넣을 내용을 고르는 쪽으로 줄여라.

작업 중 서브에이전트는 아껴 써라. 각 서브에이전트는 맥락을 다시 세우고 다시 탐색한 뒤
보고하고, 너는 그 보고를 다시 읽는다. 여러 파일에 걸친 폭넓은 조사처럼 정말 독립적이고
큰 갈래일 때만 쓰고, 검증 목적으로는 쓰지 마라.
