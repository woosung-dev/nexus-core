## 이번 세션의 목표

답변 아키텍처를 **확정하고 배선해서, 봇 설정에서 고른 대로 실제 답이 나오게** 만든다.

## 실행 방식 — 이건 지시다

**Workflow 도구로 오케스트레이션해라.** 메인 컨텍스트는 최소로 쓰고 서브에이전트가 일한다.

- 각 phase 는 `agent()` 로 띄우고, 메인은 **요약만** 받는다. 파일 내용을 메인으로 끌어올리지 마라
- 파일을 동시에 고치는 구현 에이전트는 `isolation: 'worktree'` 로 격리한다
- **리뷰는 `codex exec` 로 돌린다.** 같은 모델이 자기 코드를 보면 놓친다. 에이전트가 codex 를
  호출하고 그 출력을 정리해서 돌려주는 구조로 짜라
- 단계가 끝날 때마다 `log()` 로 한 줄 남겨라. 아침에 무슨 일이 있었는지 추적 가능해야 한다

## 절대 규칙 — 어기면 복구가 안 된다

1. **새 브랜치에서 일한다.** `feat/answer-architecture`. main 금지. **push·PR 금지.** 로컬 커밋만
2. **alembic 은 로컬 docker DB 에만.** `docker compose up db` + localhost override.
   `.env` 의 호스트명은 `db` 라 그대로 쓰면 안 된다. **Neon(라이브) 절대 금지**
3. **`frontend-admin/src/features/llm-wiki/wiki.ts`·`sources.ts` 는 skip-worktree 다.**
   해제하지 마라 — 890KB 규정집 본문이 커밋된다
4. **`exports/wiki_eval/answers.json` 은 시작 전 스냅샷을 뜬다.** 덮어써서 날린 적이 두 번 있다
5. **파괴적 명령 금지.** `rm -rf` · force push · DROP TABLE · 기존 마이그레이션 수정
6. **Gemini 예산 500회.** Phase 별 배정을 지키고, 초과가 예상되면 그 Phase 를 건너뛰고 기록해라

# Phase 2 — 근거 위반 탐지기 (codex · 대량 병렬 · 이번 밤의 핵심)

## 왜 만드나

지금 유해를 셀 수 있는 건 관리자 정답 10건 위에서뿐이다. 그런데 팔 간 격차(±0.5)와
채점 잡음(±0.6)이 같은 크기라 **n=10 으로는 아무것도 못 가른다**(핸드오프 §2-5).

정답지 없이 잴 수 있는 것이 하나 있다 — **「이 답의 주장이 규정 원문에 있는가」**.
정답이 필요 없으므로 45문항 전체, 회귀 하네스 50문항, 나중엔 실제 대화 로그까지 같은 자로 잰다.

## 이미 검증된 기법이다 — 발명하지 마라

`backend/app/services/rag/evidence.py` 를 먼저 읽어라. 프로덕션에서 도는 코드다.

```
어휘 매칭            카드 25%  ← 기각됨
LLM 추출 + 원문 대조   카드 95%  ← 채택, 가동 중
```

`snap_to_source` 가 환각을 원리적으로 막는다 — 모델이 낸 문자열을 쓰지 않고 원문 위 위치를
찾는 데만 쓰고, 못 찾으면 버린다. **이걸 뒤집으면 된다: 근거 구절을 못 찾은 주장 = 근거 없는 주장.**

## 만들 것 — `exports/wiki_eval/_audit.py`

```
1  주장 분해    답변 1건 → 사실 주장 목록 (의견·인사말·안내문구는 제외)
2  후보 검색    주장별로 BM25 멀티스케일에서 원문 후보 상위 5 (로컬 · 즉시 · 무료)
3  대조         codex: 이 주장이 후보 원문으로 뒷받침되는가 → 지지 / 미지지 / 모순
4  적대 검증    미지지·모순 판정만 3명이 각각 다른 시선으로 반박 시도
                 ① 원문 250건 전체(≈73k 토큰)를 통째로 주고 "정말 없는지" 확인
                 ② 표현만 다른 것 아닌지(존댓말·요약·동의어)
                 ③ 여러 조문에 나뉘어 있는 것 아닌지
                 2명 이상이 "근거 있다"로 뒤집으면 기각한다
5  종합         팔별 근거 위반율 + 문항별 위반 목록
```

**4-①이 핵심이다.** BM25 가 못 찾았을 뿐인 거짓양성이 반드시 나온다. 원문 전체가
컨텍스트에 들어가므로(146KB ≈ 73k 토큰) "정말 없다"를 근사가 아니라 확정으로 말할 수 있다.
codex 가 그 길이를 못 받으면 규정집/대사전 둘로 쪼개 두 번 물어라.

**팔 A 는 무엇을 검색했는지 알 수 없다**(grounding 보고가 부실하다 —
`reference_rag_grounding_underreports`). 그러니 주입한 근거가 아니라 **코퍼스 전체**에 대고
대조해라. 어차피 물어야 할 질문은 "규정이 그렇게 말하나"지 "우리가 그걸 뽑았나"가 아니다.

## 규모와 시간

```
대상    answers.json 의 rag · wiki · wiki_budget · wiki_first · hybrid  (약 190셀)
주장    셀당 5~8개  →  약 1,200건
대조    1,200회 codex
검증    미지지 추정 30% × 3명  →  약 1,100회
합계    약 2,400회 · 병렬 10 →  2~3시간 · 과금 0
```

## 내야 할 것

1. `exports/wiki_eval/audit.json` — 주장 단위 원자료
2. **팔별 근거 위반율** — 이게 프리셋 기본값을 정한다
3. **문항별 위반 목록** — "봇이 X라 하는데 규정엔 없다". 출시 게이트이자 관리자에게 넘길 목록
4. `audit_report.html` — `_golden_report.py` 와 같은 방식으로

# Phase 3 — 구현 (worktree 격리 · 병렬)

## 3a. 원문을 DB 로 (다른 것의 전제다 — 먼저 끝내라)

지금 `store.py` 가 `exports/wiki_2026-08/` 파일시스템을 직접 읽는다. 7.9MB 이고 git 이 안 본다.
**이대로는 배포가 안 된다.**

- 새 테이블 `wiki_source_units` — `src_id · doc · locator · text · sha8 · bot_id`
- 원문 250건(146KB)만 넣는다. **위키 페이지 138쪽은 넣지 마라** — 팔 C 는 기각됐다
- 적재 커맨드 (`scripts/` 관례를 따라라)
- `store.py` 의 로딩부를 crud 로 바꾼다. **인덱스·검색 로직은 그대로** (그렇게 설계돼 있다)
- 마이그레이션 `down_revision` 은 현재 head 를 확인해서 잡아라

**dense 를 뺀 덕에 벡터 저장이 필요 없다.** BM25 역색인은 기동 시 메모리에 0.01초면 선다.
캐시 파일도, 임베딩 쿼터도, 재빌드 15분도 없어졌다.

## 3b. 봇별 답변 모드 배선

- `Bot.retrieval_mode` 추가 — `file_search` | `lexical` | `both`, 기본 `file_search`
- `chat_service.py` 의 `effective_use_rag` 분기 자리에 조달 분기를 넣는다 (213~290행 근처)
- `answer_with_wiki` 를 라이브 경로에서 부를 수 있게 한다. 지금은 측정 전용이다
- **프론트엔드는 건드리지 마라.** `answer_with_wiki` 가 이미 `RAGResponse`/`RAGCitation` 을
  돌려주므로 인용 형광펜·각주가 그대로 동작한다. 이게 이 변경의 위험이 낮은 이유다

실측 근거 (프리셋 기본값):

```
file_search   57.9% · 7.0초 · 유해 3~4/10     커버리지 최고
lexical       40.2% · 1.6초 · 유해 1/10       덜 맞히고 덜 틀린다 · 세 회차 내내 안정
both          50.4% · 6.1초 · 유해 2~3/10     중간
```

## 3c. 관리자 봇 편집 화면

`frontend-admin/src/features/bots/components/bot-edit-form.tsx` 가 **575줄 단일 폼**이고
필드가 평면 나열돼 있다. 여기에 조달 모드까지 얹으면 더 나빠진다.

**탭 3개로 분해**

```
기본 정보   이름 · 설명 · 태그 · 이미지 · 플랜
답변 설정   프리셋 3장 → [고급 설정] 접기 → 축별 조정 · 시스템 프롬프트
연동        카카오 채널 · 문서 · RAG 스토어
```

**프리셋 3장** (내부적으로 `retrieval_mode` + `evidence_policy_mode` 를 함께 바꾼다)

```
정확 우선   file_search + legacy    정보 안내형 봇
균형        both + legacy           기본값
안전 우선   lexical + strict        상담·위기 봇 · 카카오(지연 민감)
```

지켜야 할 것 (근거: `ui-ux-pro-max` 스킬 조회 결과 · Data-Dense Dashboard)

- **프리셋 우선, 고급은 접어 둔다**(`progressive-disclosure`). 프리셋과 달라지면 「사용자 지정」 배지
- **각 모드에 실측 수치를 상시 표기한다** — "1.6초 · 유해 1/10". placeholder 아닌 helper text.
  규정 봇 설정 화면에서 근거를 보이는 건 이 제품의 성격에 맞는다
- **저장 전 diff 확인.** 시스템 프롬프트가 1,341자다. 이탈 시 확인 + 자동 임시저장
- 시맨틱 토큰 · Lucide 아이콘(**이모지 금지**) · 라이트/다크 둘 다 · 포커스 링 유지
- 터치 타깃 44px · 대비 4.5:1

**전면 개편은 하지 마라.** 사이드바 9메뉴 정보구조는 손대지 않는다. 이 탭 하나로 패턴만
확립하고 나머지는 출시 후에 옮긴다.

# Phase 4 — codex 교차 리뷰

구현 산출물마다 **`codex exec` 로** 리뷰한다. 같은 모델이 자기 코드를 보면 놓친다.

각 리뷰어에게 다른 시선을 줘라:

```
① 마이그레이션 안전성   down_revision 체인 · 롤백 가능성 · 기존 데이터 파손
② 라이브 회귀           이 변경이 지금 도는 채팅을 깨뜨리는 시나리오를 찾아라.
                        기본값 봇(retrieval_mode 미설정)이 지금과 똑같이 동작하는가
③ 스키마·타입 일관성     백엔드 enum ↔ 프론트 타입 ↔ API 스키마가 어긋나는 곳
④ UI 접근성             대비 · 포커스 · 키보드 · 라이트/다크
```

지적이 나오면 **고치고 다시 리뷰**한다. 2회까지. 그래도 남으면 기록만 하고 넘어가라.


**7이 가장 중요하다.** `retrieval_mode` 미설정 봇은 지금과 한 글자도 다르면 안 된다.

## 판정 기준

- **근거 위반율이 `lexical` < `file_search` 로 n=45 에서 확인되면** → 「안전 우선」 프리셋의
  근거가 선다. 고위험 봇 기본값으로 밀 수 있다
- **차이가 없으면** → `lexical` 은 지연 이점(1.6초)만 남는다. 카카오 채널용으로만 쓰고
  기본값은 `file_search` 유지
- **어느 쪽이든 배선은 남긴다.** 봇별로 고를 수 있다는 것 자체가 출시에 필요하다
