# 다음 세션 프롬프트 — 위키 1단 검색기 개선

플랜 모드로 시작할 것. 아래 `---시작---` 과 `---끝---` **사이만** 복사해 붙여넣는다.

---시작---

`docs/architecture/handoff-wiki-retrieval-2026-08-08.md` 를 먼저 읽어줘. 이번 세션의 전제와 함정이 거기 있다.

## 배경

LLM 위키를 챗봇 검색에 붙이는 실험 중이다. 45문항 × 3팔 측정에서 위키 계열이 기존 RAG에 졌다
(팔 A 기존RAG 48.0%/codex 2.40 · 팔 B 위키→원문 43.9%/1.50 · 팔 C 위키본문 36.5%/2.10).

조사 결과 진 원인이 위키가 아니라 **우리 1단 검색기**일 가능성이 크다. dense-only · 단일 스케일이라,
문헌이 가장 확실하게 개선을 보고하는 지점을 통째로 비워뒀다. 지금 접으면 교란변수를 남긴 채 접는 것이다.
검색기를 대등하게 만든 뒤 재측정하는 것이 이번 세션의 전부다.

## 할 일

### 1. 하이브리드 검색 — BM25 + dense, RRF 융합

`backend/app/services/wiki/store.py` 의 1단 검색을 바꾼다.

- BM25는 순수 파이썬으로 직접 구현한다. 외부 의존성을 추가하지 마라 — 위키 138쪽·원문 250건 규모라 충분하다.
- 한국어 토큰화에서 `제19조` · `15,000원` · `BLESSING4U` 가 끊기지 않아야 한다.
  이 도메인에서 BM25를 쓰는 이유가 이것이다.
- 검증 케이스: `"가정회비 미납이 200만원이면 얼마를 내야 하나요?"`
  현재 dense-only 는 1위로 `유아회비`(0.808)를 고르고 정답 `가정공과금`은 2위(0.790)다.
  하이브리드로 순위가 뒤집히는지 확인하고 결과를 알려줘.

근거: *"For every model, a hybrid setup improves performance across all retrieval metrics"* (arXiv 2607.06641),
작은 인코더에서 5~10pp 상승, Anthropic 실패검색 49% 감소.

외부 호출 없음. 과금 0. 반나절.

### 2. 멀티스케일 인덱스

지금은 「페이지 요약」 한 스케일만 인덱싱한다. 세 스케일을 각각 인덱싱하고 RRF로 합친다.

```
페이지 요약 138개 (현행)
원문 조문 250건
위키 사실 문장 971개
```

- **후보 풀만 늘리고 `top_k` 는 늘리지 마라.** 무관한 문서 1개만 섞여도 성능이 떨어진다(Chroma).
  팔 B가 원문 14~24건을 통째로 넣어 최하위를 한 게 정확히 이 실수다.
- 요약-only 배치가 실패라는 건 이미 외부 실증이 있다(핸드오프 §5). 원문을 반드시 같은 저울에 올려라.
- 임베딩은 무료 티어 분당 100회다. `store.py` 의 0.7초 페이싱을 우회하지 마라.

임베딩 약 1,200회(≈0.1달러). 반나절.

### 3. 재측정

```bash
cd backend
uv run python ../exports/wiki_eval/_run.py --arms A,B,C
uv run python ../exports/wiki_eval/_report.py
uv run python ../exports/wiki_eval/_grade.py     # codex, 과금 0
```

판정 기준을 셋으로 늘린다. `_report.py` 와 `_grade.py` 요약에 ③을 추가해라.

```
① 키워드 충족률    기존
② 내용 점수        기존 · codex 눈가림 채점
③ 유보 정확도      신규 — 근거 없는 문항에서 "확인되지 않습니다"로 갔는가,
                   반대로 근거가 있는데 유보해 버렸는가
```

③이 필요한 이유: 정답지 시트 ① 「"확인되지 않습니다 + 담당자 연결"만 해도 정답인가」가 **45/45 전부 "예"** 이고,
45문항 중 **위험도 '상' 이 28건**이다. 틀린 답보다 유보가 나은 판인데, 지금 채점은 유보하면 키워드 0%라
오히려 벌점을 준다. 현재값(정답 10건): 유보 A 0 · B 0 · C 1 / 유해 A 3 · B 5 · C 2.

**판정선**: 팔 A(48.0% / codex 2.40)를 못 넘으면 3안 종료. 단 ③에서 위키 계열이 뚜렷이 앞서면
그것만으로 채택 근거가 되니 따로 보고해라.

10분. 약 2달러.

### 4. (1~3이 끝나고 여유가 있으면) 팔 D — 검색 없이 통째 주입

원문 250건 전체가 약 72,851 토큰이다(위키 138쪽은 111,130). Anthropic 가이드는 20만 토큰 이하면
RAG 없이 통째로 넣어도 된다고 한다. 검색을 0으로 만든 **상한선**을 재기 위한 팔이고,
프로덕션 후보는 아니다. 여유가 없으면 건너뛰어라.

## 공정성 규칙 — 깨지 말 것

모델(`gemini-3.5-flash-lite`) · 온도 0.3 · `max_tokens` · `system_prompt`(봇 11 DB값) ·
근거지시 문구(`GUIDE`)를 세 팔에 **동일하게** 건다. 다른 것은 "근거를 무엇으로 주느냐" 하나뿐이다.
한쪽 프롬프트에만 지시를 넣지 마라 — 과거에 팔 B에만 "원문에 근거해서만 답하라"가 들어가 있었고,
그대로 뒀으면 검색 성능이 아니라 지시 문구를 잰 결과가 나왔다.

## 함정

- `_run.py --limit N` 이 `answers.json` 을 N행으로 덮어썼던 사고가 있었다. 지금은 병합하도록 고쳤지만,
  결과 파일을 건드리는 변경을 했으면 45행이 남아 있는지 확인해라.
- 위키를 재생성했으면 `exports/wiki_2026-08/bots/11/_index.json` 을 지우고 다시 만들어라.
  캐시는 페이지 슬러그 목록으로만 검증해서, 요약 내용만 바뀌면 안 깨진다.
- `frontend-admin/src/features/llm-wiki/wiki.ts`·`sources.ts` 는 `skip-worktree` 상태다.
  해제하면 890KB 규정집 본문이 커밋된다.
- `_run.py` 에 로깅 설정이 없어 배치 실행 시 HTTP 호출 기록이 파일에 안 남는다. 감사 근거가 필요하면 먼저 붙여라.
- 채점 자 두 개(키워드·내용)가 순위를 다르게 낸 전례가 있다. 하나만 보고 판정하지 마라.

## 작업 방식

- 요청한 범위만 해라. 애매하면 판단해서 진행하고, 해석에 따라 결과물이 크게 달라질 때만 물어봐라.
  더 나은 접근이 보이면 한 문장으로 말하고 요청한 대로 계속 진행해라.
- 서브에이전트는 쓰지 마라. 이 작업은 한 컨텍스트에서 끝난다.
- 각 단계가 끝나면 **결과부터 한 줄로** 말하고 근거를 뒤에 붙여라. 중간 내레이션은 방향이 바뀔 때만.
- 문서를 새로 쓰지 마라. 기존 핸드오프에 결과만 갱신해라.
