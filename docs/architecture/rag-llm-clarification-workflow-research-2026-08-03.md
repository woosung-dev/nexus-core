# RAG·LLM 기반 맥락 보완 워크플로우 조사 (2026-08-03)

## 결론

가능하다. **LLM이 RAG 근거를 읽은 뒤 추가 질문 필요 여부를 스스로 결정**하게 만들 수 있다. 다만 모델에게 자연어 문장만 받는 방식은 선택지 환각과 JSON 형태 변형이 생길 수 있으므로, 권장안은 **`RAG + 동일 LLM의 단일 계획 호출` + `구조화 출력·근거 검증`**이다.

여기서 애플리케이션의 역할은 “어떤 주제는 무조건 질문”이라고 대신 결정하는 것이 아니다. LLM이 낸 결정(`ask`/`answer`)과 질문을 형식·근거 관점에서 검증하고 표시하는 오케스트레이터다. 근거 검증에 실패하면 임의의 질문을 만들어 내지 않고, 일반 RAG 답변으로 안전하게 전환한다.

## 현재 MVP와 차이

현재 시도도 첫 단계에서 RAG와 LLM을 함께 사용해 질문 여부를 판단하려는 방향이다. 하지만 실제 테스트에서 아래 두 경우가 드러났다.

1. LLM이 `ready`를 내리면 질문 없이 요약 화면으로 전환된다.
2. LLM이 질문·선택지의 JSON 필드 모양을 다르게 만들면 서버 검증에 실패해 폴백으로 전환된다.

따라서 “질문을 할지 LLM이 판단한다”는 목표 자체는 맞지만, 결정의 의미와 출력 계약을 더 엄격히 해야 한다. 특히 `ready`는 “바로 최종 답변이 충분히 정확하다”일 때만 허용해야 하며, 단순히 질문을 찾지 못했다는 뜻으로 쓰면 안 된다.

## 선택지 비교

| 방식 | 질문 여부 결정자 | 최초 요청당 모델/RAG 호출 | 장점 | 한계 | 적합도 |
|---|---:|---:|---|---|---|
| LLM 단독 | LLM | 1 | 가장 간단 | 문서에 없는 절차·선택지를 만들 수 있음 | 비추천 |
| 고정 슬롯/설문 | 규칙·운영자 | 0~1 | 가장 예측 가능 | 모든 주제에 질문이 강제되고 관리 부담이 큼 | 특정 고위험 업무에만 |
| 다단계 에이전트 | LLM + RAG | 질문 수만큼 증가 | 앞 답변에 맞춰 다음 질문을 바꿀 수 있음 | 지연·비용·상태 관리가 커짐 | 복잡 상담에만 |
| **RAG 기반 단일 계획 + 검증** | **LLM** | **1** | 한 번에 최대 3개 질문, 문서 근거, 빠른 UX | 첫 카드 이후 동적 재질문은 하지 못함 | **권장** |

## 권장 구조

```text
사용자 최초 요청
  → Gemini 3.5 Flash-Lite + File Search (1회)
      └─ 질문 필요성 판단 + 최대 3개 질문 + 문서 인용을 JSON으로 반환
  → 서버 스키마·근거 검증
      ├─ ask  : 인라인 카드 한 장에 질문들을 모두 표시
      ├─ answer: 바로 최종 RAG 답변 생성으로 전환
      └─ invalid/근거없음: 질문을 꾸며내지 않고 최종 RAG 답변 또는 “문서 근거 부족” 안내
  → 사용자가 카드 답변/직접 입력/수정
  → 확정 요약으로 Gemini 3.5 Flash-Lite + File Search (최종 답변 1회)
```

### 최초 계획 호출의 역할

하나의 RAG 호출에서 아래를 **모두** 받는다. 질문이 여러 개인 경우에도 추가 호출하지 않는다.

```json
{
  "decision": "ask",
  "reason": "축복 유형과 현재 단계에 따라 문서상 안내가 달라집니다.",
  "questions": [
    {
      "id": "blessing_type",
      "title": "어떤 축복 관련 안내가 필요하신가요?",
      "kind": "single",
      "options": ["1세 축복", "2세 축복", "잘 모르겠어요"],
      "allow_custom": true,
      "evidence": ["문서명/인용 ID"]
    }
  ],
  "direct_answer_allowed": false,
  "citations": ["문서명/인용 ID"]
}
```

`decision = answer`는 “현재 질문만으로 문서 근거를 가진 정확한 답을 낼 수 있다”일 때만 선택하게 한다. `질문을 찾지 못함`, `검색 결과가 약함`, `형식 오류`는 `answer`의 근거가 아니다.

### 질문 생성 프롬프트·검증 규칙

1. 모델은 검색된 문서와 사용자 요청만 근거로 삼는다. 근거에 없는 행사명·단계·서류·자격을 옵션으로 만들지 않는다.
2. 추가 정보가 바뀌면 **답변 내용 또는 다음 행동이 실제로 달라지는 경우**에만 질문한다. 이 반사실 테스트를 통과하지 못하면 바로 답한다.
3. 한 번에 질문은 최대 3개, 각 질문은 답변 차이를 설명하는 `reason`과 인용을 가진다.
4. 선택지는 인용된 문서의 명칭을 그대로 쓰거나, 개인 상황을 묻는 중립 문장으로만 쓴다. 후자는 `기타/직접 입력`을 반드시 함께 제공한다.
5. 서버는 JSON Schema, 최대 개수, 중복, 질문별 인용 존재, 인용이 현재 검색 결과에 포함됐는지를 검증한다. 구조화 출력만으로 의미적 정확성은 보장되지 않는다는 Gemini의 주의사항을 반영한 것이다.
6. 검증 실패 시 “LLM 판정 실패”라고 사용자를 멈추게 하지 않는다. 질문 카드를 생략하고, 원래 요청으로 RAG 답변을 제공하거나 근거 부족을 명확히 알린다.

## UX 권고

- 질문은 대화풍 여러 턴보다 **한 장의 인라인 카드**에 묶는다. Microsoft의 안내처럼 옵션과 직접 입력을 함께 둬 질문 횟수와 이탈을 줄인다.
- 카드 상단에는 `답변을 더 정확히 하기 위해 최대 3가지만 확인할게요`라고만 설명한다. 내부 표현인 `LLM 판정`, `RAG`, `폴백`은 사용자 UI에 노출하지 않는다.
- `건너뛰고 답변 보기`를 유지한다. 이 경우에도 최종 RAG 답변이 나오며, 답변 안에서 “개인 상황에 따라 달라질 수 있는 항목”만 짧게 명시한다.

## 검증 지표

출시 전에는 실제 D-1 문서와 대표 질문으로 아래를 측정한다.

| 지표 | 통과 기준 제안 |
|---|---|
| 질문 근거 누락률 | 0% |
| 근거 없는 절차/용어 생성률 | 0% |
| 필요한 분기에서 `answer`를 선택한 비율 | 표본 검수로 5% 이하 |
| 불필요 질문 비율 | 표본 검수로 10% 이하 |
| 최초 카드 생성 호출 수 | 요청당 정확히 1회 |
| 카드 후 최종 답변 호출 수 | 확정/건너뛰기 시 정확히 1회 |
| 사용자 직접 입력·건너뛰기 완료율 | 이벤트로 관찰 후 기준 설정 |

## 권장 결정

**RAG 기반 단일 계획 + 검증**으로 진행한다. 모델은 질문 여부를 결정하되, 그 결정과 모든 선택지를 검색 근거에 묶고, 서버는 형식·인용만 검증한다. 이는 “운영자가 모든 분기표를 미리 작성하지 않으면서도” 현재 발생한 비근거 선택지와 포맷 오류를 막는 가장 작은 구조다.

첫 번째 구현 범위는 다음으로 충분하다.

1. Gemini 3.5 Flash-Lite File Search 호출의 출력을 엄격한 `ClarificationPlan` JSON Schema로 교체한다.
2. 카드에는 한 번에 최대 3개 질문을 표시하고, 답변 단계에서 LLM을 재호출하지 않는다.
3. 인용 없는 질문·옵션은 버리고, 카드 전체가 무효라면 곧바로 원 요청의 RAG 답변으로 전환한다.
4. D-1의 ‘1세/2세 축복’, ‘가정출발’, ‘교육/행정’ 표본을 각각 평가셋으로 만들어 질문 필요성·근거를 검수한다.
