# 근거 위반율 — 45문항 전수 (2026-08-10)

> **이 문서가 지어냄율의 최신 정본이다.** `handoff-overnight-2026-08-10.md` §1·§2 의 표는
> 25문항 표본이고, **순위가 다르다**. 인용하기 전에 아래 표로 대조할 것.
> 자와 방법론은 그 문서 §1 이 그대로 유효하다 — 바뀐 것은 표본 수와 결과뿐이다.

## 0. 30초 요약

어젯밤 쿼터 소진으로 77셀이 비어 있던 것을 채워 **225셀(45문항 × 5팔) 전수**로 다시 쟀다.

**결론 하나가 뒤집혔다.** 25문항에서 "`both` 가 최악"이라 판단했는데, 전수에서는
**현재 기본값인 `file_search` 가 가장 많이 지어낸다(14.2%).**

`both` 를 권하지 않는 결론 자체는 유지된다 — 근거가 「지어냄율 최악」에서 **「모순 최다」**로 바뀔 뿐이다.

## 2. 무엇이 뒤집혔나

```
25문항(148셀):  C 1.4 < B′ 2.7 < B 5.4 < A  8.2 < F 11.2    ← F 최악
45문항(225셀):  C 2.6 < B′ 3.4 < B 4.1 < F 11.4 < A 14.2    ← A 최악
```

**A 와 F 의 순위가 바뀌었다.** A 는 8.2% → 14.2% 로 크게 악화됐고 F 는 11.2% → 11.4% 로 거의 그대로다.
즉 25문항 표본에서 A 가 유난히 좋게 나왔던 것이지, F 가 나빠진 것이 아니다.

`handoff-overnight-2026-08-10.md` §2 의 *"F 가 다섯 팔 중 최악"* 과
머지된 PR #53 본문의 같은 서술은 **전수에서 성립하지 않는다.**

## 3. 그래도 `both` 를 기본값으로 하면 안 된다 — 근거가 바뀔 뿐

| | A `file_search` | F `both` |
|---|---|---|
| 지어냄율 | 14.2% | 11.4% |
| **모순** | 3건 | **6건** |
| 커버리지 | 56.6% | 50.1% |

**모순은 원문이 다르게 말하는, 가장 나쁜 종류다.** F 가 A 의 2배다.
커버리지는 중간인데 모순은 최다라는 구조가 전수에서도 그대로다.
「균형」 카드의 *"권장하지 않는다"* 표기는 유지한다.

## 4. 「안전 우선」 프리셋 — 근거가 강해졌다

```
lexical 3.4%  vs  file_search 14.2%   →  4.2배   (25문항에서는 3배)
모순     0건   vs  3건
지연     1.9초 vs  7.3초
```

대가는 커버리지 −12.4pp(44.2% vs 56.6%)와 무주장 셀 6개다.
**틀린 답보다 모른다는 답이 나은 경로 — 상담·위기·카카오 — 의 근거는 더 단단해졌다.**

## 5. 「덜 말해서 덜 지어낸다」로 설명되지 않는다

이 자의 알려진 약점은 말수가 적은 팔이 유리해 보인다는 것이다. 전수에서는 그것으로 설명되지 않는다.

```
A   무주장 0셀 · 주장 338건 · 셀당 지어냄 1.07
C   무주장 9셀 · 주장 230건 · 셀당 지어냄 0.13
```

**주장 수는 1.47배인데 셀당 지어냄은 8배다.** 발화량 차이보다 격차가 훨씬 크다.
다만 무주장 셀·주장 수는 앞으로도 표에 함께 싣는다.

## 6. 재현 방법과 함정

```bash
# 빈 셀만 다시 채운다 (성공셀은 건드리지 않는다)
cd backend && uv run python -u ../exports/wiki_eval/_run.py --arms A,B,B2,C,F --retry-failed
cd backend && uv run python -u ../exports/wiki_eval/_audit.py --stage all   # resume-safe · Gemini 0회
python3 exports/wiki_eval/_audit_report.py
```

**⚠ `--retry-failed` 없이 재실행하면 안 된다.** `_run.py` 는 원래 성공한 셀도 다시 불렀다.
답변이 새로 생성되면 **이미 감사한 셀의 결과와 어긋난다** — 과금이 아니라 비교 가능성 문제다.
이번에 이 플래그를 추가했고, 실행 전 스냅샷 `answers_prev.json` 과 대조해 확인했다:

```
성공셀 그대로 148 · 변경 0 · 신규 77 · 남은 빈 칸 0  →  225/225
```

감사도 resume-safe 다 — 225셀 중 기존 148개는 건너뛰고 새 77셀만 codex 로 처리했다(약 7분).

산출물: `exports/wiki_eval/audit_report.html` (225셀 · 위반 143건 / 30문항) ·
`exports/wiki_eval/report.html` (키워드 커버리지).

## 7. 이 결과가 바꾸는 것

**현재 라이브 봇 21개가 전부 `file_search` 다 — 즉 가장 많이 지어내는 설정으로 돌고 있다.**
`retrieval_mode` 배선은 #53 으로 이미 배포됐으므로, 바꾸는 데 필요한 것은 코드가 아니라 판단이다.

다음 단계는 순서대로:

1. 규정집을 라이브 DB 에 적재한다(`wiki_source_units` 가 0행이면 `lexical` 을 켜도 못 쓴다)
2. 시험용 봇 하나만 `lexical` 로 돌려 관찰한다
3. 괜찮으면 상담·위기·카카오 경로부터 바꾼다

기본값 자체를 `lexical` 로 바꿀지는 커버리지 −12.4pp 를 감수할지의 문제라 별도 결정이다.
