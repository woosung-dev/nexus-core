   시드 규칙 4개가 혼자 정했다가 표적을 통째로 놓쳤다
② 규칙을 DB 에 넣고 **관리자 화면 「추가 확인 질문 정책 → 테스트하기」로 먼저 확인한다**
   배선 전에 규칙이 실제로 걸리는지 LLM 없이 확인된다
③ 배선한다
④ **프론트가 선택지를 그리게 한다** ← 문서 §3 에 없는 단계다. 아래를 읽어라

## 문서가 틀린 곳 — 2026-08-10 에 확인했다

핸드오프가 쓰인 뒤 코드와 라이브가 움직였다. **문서보다 이 세 줄이 우선한다.**

1. **§6 「169 통과」 → 실제 175.** PR #59(strict 게이트)가 6개를 더했다. 정상이다

2. **§5 「봇 11에는 변화가 없다」가 더 이상 참이 아니다.**
   라이브 봇 11(D-1 ver2)이 이미 `retrieval_mode='lexical'` 이고 위키 138쪽·원문 250건이
   라이브 DB 에 적재돼 있다. 문서와 PR #58 은 「라이브 전부 `file_search`」를 전제로 썼다.
   **삽입점인 어휘 분기가 곧 주력 봇의 라이브 경로다.** 실험용 우회로가 아니라 본선이다

3. **삽입점 바로 그 자리에 strict 게이트가 생겼다** (`chat_service.py:613` `_strict_blocks`).
   되묻기 응답을 `rag_response.answer` 에 넣으면, strict 봇에서 그 질문은 인용 0건이고
   거절문도 아니라 **`STRICT_EVIDENCE_MESSAGE` 로 치환된다 — 봇이 되물은 질문이 삼켜진다.**
   지금은 라이브 11봇이 전부 `evidence_policy_mode='legacy'` 라 안 터지지만, strict 를
   켜는 순간 터진다. **되묻기 삽입은 strict 게이트 뒤에 놓고, 그 순서를 주석으로 남겨라**

## ④ 프론트 — 여기가 실제 비용의 큰 몫이다

문서 §5 마지막 줄이 그렇게 적어 뒀는데 정작 단계 목록에 없다. 확인한 사실:

```
frontend-client/src/app/(protected)/chat/ChatProvider.tsx:290-300
  → 완성 응답에서 `content` 와 `followups` 둘만 읽는다
frontend-client/src/components/chat/ChatArea.tsx
  → ask / handoff / clarif 참조 0건
frontend-client/src/components/chat/ClarificationPrototype.tsx:185-194
  → ask / ready / handoff 렌더가 여기 있다. 이걸 ChatArea 로 올려야 한다
```

**선택지를 못 그리면 ⑤ 측정 자체가 불가능하다** — 되물은 뒤 품질을 재려면 사용자가
선택지를 눌러야 한다. 프론트를 이 세션에서 안 할 거라면, ⑤ 를 「API 직접 호출로 측정」
이라고 범위를 좁혀 명시하고 프론트는 다음 세션으로 넘겨라. 둘 중 하나를 고르되
**말없이 ⑤ 를 건너뛰지는 마라.**

## ① 의 크기 — 문서가 암시하는 것보다 크다

시드 규칙 4개(`docs/architecture/clarification-policy-seed-2026-08-11.json`)를 확인했다.
`eligibility-age` 의 예시질문이 「미성년자도 축복을 받을 수 있어」인데 이건 45문항 **#13**
이다. 시드는 #13·#16 을 겨냥했고 실패 5건과 겹치지 않는다는 §3① 주장이 맞다.

그리고 **#36(축복정리)·#45(B4U)는 대응할 시드 규칙이 아예 없다.** 새로 2개를 처음부터
써야 한다. 규칙 5개 × 슬롯 확정 인터뷰다.

> `request_examples` 가 매칭의 전부다. BM25 가 「질문 대 관리자 예시질문」을 비교한다.
> 예시가 실제 질문과 같은 어휘를 안 쓰면 규칙이 안 걸린다.

## 제약

- **판정 축을 바꾸지 마라.** `needs_user_input`(질문자만 아는 것이 빠졌나)이지
  `answerable`(답할 수 있나)이 아니다. 후자는 45문항 중 35건(78%) 발동해서 못 쓴다
- **되물을 문구를 LLM 이 짓게 하지 마라.** 관리자가 쓴 슬롯 문구를 그대로 꺼낸다
- **되묻기는 한 번까지.** 프롬프트 3번 항목이 이미 그렇게 정해 뒀다
- **라이브 DB 는 읽기만.** 로컬 검증용 복제봇이 봇 29 다 (D-1 ver2 · 1,341자 · lexical)
- 나머지 제약은 §4, 함정은 §5. 특히 **`both` 는 삽입점이 없고**(`build_hybrid_turns` 가
  `Retrieved` 를 함수 안에서 버린다), **0라운드 근거 재사용은 아직 안 된다**

## 확인

문서를 믿기 전에 §0 과 §6 의 확인 명령을 돌려라. 값이 다르면 그 사이에 코드가 바뀐

「봇 11 · clarify_enabled=true 0 · 규칙 보유 봇 0」이 그대로 나왔다.

## 이 세션에서 사용자에게 물어야 할 것

**실패한 5건이 각각 어떤 슬롯으로 갈리는가.** 판정기가 짚은 후보가 §3① 표에 있지만
그게 맞는지는 규정 지식이다. 이걸 틀리면 규칙 전체가 헛돈다.

물어야 할 것이 생기면 그때 한 번에 묶어서 물어라. 답을 기다리는 동안 그 답에
의존하지 않는 일(확인 명령, 코드 읽기, 프론트 조사)을 먼저 끝내 둬라.

## 이 프롬프트를 이렇게 쓴 이유

**§0 을 맨 앞에 못 박았다.** 규칙이 0개라 지금 배선하면 되묻는 대신 전부
「담당자에게 문의하세요」로 빠져 지금보다 나빠진다. 이걸 앞에 안 두면 다음 세션이
"코드 다 있네" 하고 바로 배선한다.

**①은 혼자 하지 말라고 적었다.** 어떤 슬롯으로 답이 갈리는지는 규정 지식이다.
시드 규칙 4개가 그걸 혼자 정해서 표적을 놓쳤다.

**「문서가 틀린 곳」을 제약보다 앞에 뒀다.** 핸드오프는 확인 명령이 붙은 사실 목록이지만
그 사이에 라이브와 코드가 움직였다. 특히 3번(strict 게이트가 삽입점에 생긴 것)은
지금 안 터지고 나중에 터지는 종류라, 배선하는 사람이 모르면 못 찾는다.

**④를 단계로 승격했다.** 문서는 프론트를 §5 제약 목록 안에 한 줄로 묻어 뒀는데,
거기가 실제로는 일정의 절반이고 ⑤ 의 선행 조건이다.
