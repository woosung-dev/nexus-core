## 결론

**배선은 됐고, 프리셋 기본값의 근거도 섰다.** 봇 설정에서 고른 대로 실제 답이 나온다
(`file_search` · `lexical` · `both`). 기본값 봇은 인자 단위로 변경 전과 동일함을 테스트로 증명했다.

정답지 없이 재는 자를 만들어 **팔별 「지어냄율」**을 처음으로 얻었다.
**어휘 검색(lexical)이 의미 검색(file_search)보다 3배 덜 지어낸다** — 「안전 우선」 프리셋의 근거다.

**못 한 것 (Gemini 하루 쿼터 소진 · 리셋 KST 16:00)**

**예상과 달랐던 것 둘. 둘 다 설계 변경으로 이어졌다.**
1. **`both`(균형 프리셋)가 가장 많이 지어낸다** — 기본값 후보에서 내렸다(§2)

## 1. 근거 위반율 — 이번 밤의 산출물

「이 답의 주장이 규정 원문에 있는가」를 잰다. 정답지가 필요 없다.
**지어냄 = 규정 원문 250건에도 시스템 프롬프트에도 근거가 없는 사실 주장.**

### 주표 — 5팔 완비 25문항

| 팔 | 셀 | 무주장 셀 | 주장 | 지어냄 | 프롬프트 출처 | 모순 | 지어냄율 | 셀당 |
|---|---|---|---|---|---|---|---|---|
| **C** 위키 본문 | 25 | 5 | 138 | 2 | 6 | 0 | **1.4%** | 0.08 |
| **B′** 예산 3,000자 (= `lexical`) | 25 | 6 | 146 | 4 | 7 | 0 | **2.7%** | 0.16 |

| 팔 | 셀 | 주장 | 지어냄 | 모순 | 지어냄율 |
|---|---|---|---|---|---|

비교식 채점이 아니라 원문 대조라서다.

### 반드시 함께 읽을 것 — 말을 적게 하면 지어낼 것도 적다

C 는 25셀 중 **5셀에서 아무 사실 주장도 하지 않았고** 주장 총수도 A 의 2/3 다.
지어냄율이 낮은 것은 부분적으로 「덜 말해서」다. 그래서 무주장 셀·주장 수를 항상 같이 놓았다.
커버리지는 반대 방향이다(A 57.9% vs B′ 40.2%, 핸드오프 §2-2). **이 맞교환이 프리셋의 전부다.**

| 검증 | 결과 |
|---|---|

## 2. 프리셋 기본값 — 판정

지시서의 판정 기준: *"위반율이 `lexical` < `file_search` 로 확인되면 「안전 우선」의 근거가 선다."*

**확인됐다. 2.7% vs 8.2% (주표) · 2.9% vs 10.0% (부표).** 3배 차이이고 두 표에서 일치한다.
`lexical` 은 지연 이점(1.6초 vs 7.0초)만 있는 것이 아니다.

**그런데 `both` 를 기본값으로 밀면 안 된다.**

```
F(both)  지어냄 11.2% · 모순 5건   ← 다섯 팔 중 최악. 모순은 A 의 5배
A(단독)  지어냄  8.2% · 모순 1건
```

의미 검색에 원문을 얹으면 커버리지는 중간(50.4%)인데 **지어냄과 모순은 늘었다.**
근거가 두 갈래로 들어오면 모델이 그 사이를 메우는 것으로 보인다 —
핸드오프 §2-4 의 「이어 붙이기가 유해 최다」와 같은 방향이다.

실제 모순 예 (#43 · `both`):

```
기성축복의 축복감사헌금은 500,000원이다.     ← 원문이 다르게 말한다
독신축복의 축복감사헌금은 1,000,000원이다.   ← 원문이 다르게 말한다
```

**그래서 관리자 화면의 「균형」 카드에 "권장하지 않는다"를 명시해 두었다.**
기본값은 `file_search` 유지, 상담·위기·카카오 봇은 「안전 우선」(`lexical`+`strict`).

### 설계에서 지시서와 달라진 것 (근거 있음)

**(1) 위키 페이지 138쪽도 DB 에 넣었다.** 지시서는 "넣지 마라 — 팔 C 는 기각됐다" 였는데,
그건 *위키 본문으로 답하기*(팔 C)의 기각이지 *검색 신호*를 버리라는 뜻이 아니었다.
페이지의 `## 사실` 문장 971개가 RRF 융합의 세 순위표 중 하나다. 빼고 45문항을 재보니:

```
raw_budget 실제 주입 목록이 완전 동일   2/45 (4%)
자카드 평균                           0.47
reg-100(29,774자 부칙 모음) 주입        1/45 → 19/45
```

reg-100 은 3,000자 예산을 통째로 먹는 유닛이라, 42% 의 질문에서 진짜 근거가 밀려났다.
답변 본문으로는 여전히 쓰지 않는다 — 검색용으로만 싣는다.

**(2) `WIKI_DENSE_SCALES` 기본값을 `""`(BM25 전용)로 바꿨다.** 코드 기본값은
`page,unit,fact` 였다. 그대로 두면 `lexical` 봇의 **첫 요청에서 1,401건을 임베딩**해
하루 상한(1,000회)을 넘기고 15분간 멈춘다. 측정 하네스는 늘 `""` 를 명시했기 때문에
지금까지 드러나지 않았던 배포 지뢰다.

**(3) 감사기에 ③′ 인용 스냅 검증을 추가했다.** 지시서에 없던 단계다.
codex 가 "지지한다"며 없는 구절을 지어내면 위반율이 과소평가되므로,
`evidence.py:snap_to_source` 로 그 인용이 원문에 실재하는지 확인한다.
(이번 실행에서는 0건 발동 — codex 가 인용을 지어내지 않았다.)

## 5. codex 교차 리뷰 — 지적과 처리

네 시선(마이그레이션 · 라이브 회귀 · 스키마 일관성 · UI 접근성)으로 돌리고, 고친 뒤 한 번 더 돌렸다.

### 고친 것

| 지적 | 처리 |
|---|---|
| **배포 이미지에 `exports/` 가 없으면 `FileNotFoundError` 가 500 으로 샌다** | `WikiCorpusUnavailable` 예외를 새로 두고 `chat_service` 가 잡아 `file_search` 로 폴백 |
| **어휘 검색이 빈손이면 빈 답변 200 이 나간다** (동의어·구어체 질문) | 답변이 공백이면 `file_search` 로 폴백. 테스트 3건 추가 |
| `_INDEX_CACHE` 가 재적재 후에도 낡은 원문을 들고 있다 | `clear_index_cache()` 추가 (적재 스크립트 실행 뒤 프로세스 재시작 또는 호출) |
| 탭에 화살표·Home/End 키 이동과 roving tabIndex 가 없다 | 구현. 탭 3개가 Tab 순서를 세 번 잡아먹던 것도 해소 |

| 저장 안 한 변경 경고가 취소 버튼에서만 뜬다 | `beforeunload` 추가 (새로고침·주소창·탭 닫기) |
| 라이트 모드 `text-amber-600` 대비 3.3:1 | `amber-700` 로 교체 |

재리뷰 결과 남은 지적 1건: **빈 답변 폴백 시 모델 호출이 2회가 된다.**
의도한 맞교환이다 — 빈 답변은 사용자에게 그냥 고장이고, 이 경로는 생성이 실패했을 때만 탄다
(검색이 빈손이면 `answer_with_wiki` 가 Gemini 를 아예 부르지 않는다). 로그로 구분된다.

### 기록만 하고 넘어간 것

- **`gpt-*` 봇에도 `lexical` 을 저장할 수 있다.** 런타임은 `file_search` 로 폴백하고
  관리자 화면에도 경고를 띄우지만, API 레벨에서 막지는 않는다. 나중에 프로바이더가 늘 수 있어서다.
- **클라이언트용 `/api/v1/bots` 가 `retrieval_mode` 를 노출한다.** 같은 `BotResponse` 를 쓴다.
  다만 **`system_prompt` 가 이미 같은 경로로 공개 노출돼 있다** — 이쪽이 훨씬 큰 선재 문제다.
  공개용 스키마 분리는 별건으로 다뤄야 한다.
- **`wiki_pages.sources` 가 `src_id` 문자열만 담아 판본(`sha8`)을 참조하지 않는다.**
  한 봇이 v20·v21 을 동시에 연결하면 `reg-33` 이 어느 판본인지 모호해진다. 지금은 봇당 판본이
  하나뿐이라 문제가 없다. 판본 병행을 시작하면 그때 `(sha8, src_id)` 로 바꿔야 한다.
- **`bots` 에 컬럼을 추가하는 DDL 은 `ACCESS EXCLUSIVE` 락을 잡는다.** `lock_timeout` 이 없어
  긴 트랜잭션이 열려 있으면 무기한 대기한다. 라이브 적용 시 한산한 시간에 할 것.

## 6. 알려진 회귀·미결

- **`lexical`/`both` 는 `followups` 가 빈 배열이다.** `answer_with_wiki` 가 채우지 않는다.
  카카오 워커가 followups 를 쓴다(`kakao_worker.py:73`). 지연이 `lexical` 의 값어치라
  추가 LLM 호출로 메우지 않았다 — **의도된 맞교환**이다.
- **비스트리밍 강제는 아무것도 깨지 않는다.** 조사 결과 두 프론트엔드 어디에도 SSE 파서가 없고
  (`text/event-stream` 은 백엔드 1곳에만 존재), 웹 클라이언트는 이미 `stream: false` 를 보내고
  JSON 만 파싱한다(`ChatProvider.tsx:277,284`). 스트리밍 분기는 웹 경로에서 사실상 사문이다.
- **웹 클라이언트는 응답의 `citations` 를 무시하고** `/chats/{id}/messages` 를 2초×15회 폴링해
  DB 백필을 기다린다(`ChatProvider.tsx:309-364`). 위키 경로 인용도 이 경로로 흐르므로 동작한다.
- **`bot-form.tsx`(봇 생성)에는 `retrieval_mode` 가 없다.** 새 봇은 서버 기본값 `file_search` 로
  만들어지고 수정 화면에서 바꾼다. 의도된 범위 제한이다.
- **배포 순서 주의**: 모델에 `retrieval_mode` 가 생겼으므로 **마이그레이션을 먼저 적용해야**
  라이브 쿼리가 안 깨진다. 이번 밤에 실제로 이 순서로 한 번 깨졌다(감사 스크립트가 Neon 을 읽다가).
